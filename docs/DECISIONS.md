# Decisions — Shield

Settled choices, so they are not re-litigated mid-project. What was decided,
and why. Newest last, numbered, never renumbered.

## How to read this file

**An entry is never edited to make it look right later, and never deleted.**
The reasoning is the record — including the reasoning that turned out to be
wrong, because "why did they do that" is the question this file exists to
answer, and a decision quietly rewritten answers it falsely. When a choice
changes, a **new entry** is written giving the new reason, and the old entry
gets a marker on its title line pointing at it.

Three markers, and they mean different things:

| Marker | Meaning |
|---|---|
| **SUPERSEDED BY n** | No longer in force. Entry *n* replaces it. Do not act on this one. |
| **AMENDED BY n** | Still in force, with a stated exception or narrowing in *n*. Read both. |
| **REVERTED BY n** | Was built, did not work, and was taken back out. *n* says what happened. |

An entry with no marker is in force.

## What this file is not

It is not a task list — that is docs/TASKS.md — and it is not a changelog.
A decision goes here when the reasoning would otherwise be lost and somebody
would later have to re-derive it, or worse, re-make the same mistake.

1. **Project name is "Shield"**
   — Directly describes the core mechanism — detecting and hiding identifiable elements, locally, at the screen level.
2. **Target browser is Chrome only (for hackathon)**  — **SUPERSEDED BY 214** — Firefox is a supported target; Chrome stays the primary demo.
   — Simplifies the build significantly for a hackathon timeline. WebGPU support in Chrome is solid and well-documented. Multi-browser support is architected for (see ROADMAP.md Phase 5) but not built now.
3. **Explore free-tier options first for the server-side AI model, no paid API committed to yet**
   — Keeps project cost near zero during development.
4. **Primary demo task is login/form autofill**
   — Simplest, most relatable task to show live; naturally showcases every mandatory requirement in one clear flow.
5. **Secondary demo tasks (if time allows): multi-field signup form, then video call/profile photo face detection, in that order**
   — Proves generalization beyond one hardcoded page. Signup form first (lower risk, reuses DOM logic); face detection second (higher risk, different code path).
6. **DOM-based detection is the primary signal for form-based PII; the visual model is a secondary/supplementary signal**
   — DOM attributes are cheap and highly reliable. The visual model's real value is catching what DOM signals structurally cannot (faces, on-screen text).
7. **When uncertain whether something is sensitive, default to hiding it**
   — A missed PII item is a more serious failure than an over-redacted safe item, both for real-world safety and for the evaluation rubric's PII recall weighting.
8. **No AI-tool traces in the codebase (comments, commit messages, file headers)**
   — Codebase should read as the team's own engineering work.
9. **Expand all project documentation to full production-grade depth, not just hackathon-MVP level**
   — The team wants a genuinely complete plan — covering security/threat model, API contracts, full risk register, and a post-hackathon roadmap — not just what's minimally needed to pass judging. This does not change what gets BUILT for the hackathon (still Phase 1 core first, per TASKS.md) — it changes…
10. **Server action vocabulary is a fixed allowlist (click, type, scroll), validated on both server and client**
   — Bounds the security blast radius of any reasoning-model error or manipulation — the server can never cause arbitrary code execution or undefined behavior on the client, only a pre-approved, safe set of actions.
11. **Redaction uses semantic placeholder tokens (e.g. `[PASSWORD]`, `[NAME]`) instead of blind blackout/deletion**
   — Preserves page structure so the cloud reasoning model can still interpret the page correctly, directly protecting the accuracy score (25% weight) while keeping the privacy guarantee fully intact.
12. **Extension client is written in TypeScript, built with Vite**
   — TECH_STACK.md left this open ("JavaScript or TypeScript"). TypeScript wins because the central risk in this project is a wiring mistake that hands unredacted data to the transport layer, and a type system can make that a build failure instead of a live incident.
13. **The redact-before-transmit invariant is enforced by a phantom type — `Sanitized<T>` in `extension/src/lib/types.ts`, branded with a non-exported `unique symbol`**
   — Only the Redaction Engine can mint a `Sanitized<T>`, and the Transport Layer accepts nothing else, so passing unredacted data to the network is a compile error rather than something we hope code review catches.
14. **A second, independent runtime guard tracks which pipeline stages actually completed, and refuses to advance past `sending` unless `redacting` ran**
   — The type seal catches bad wiring at build time but cannot catch a stage that was entered and then threw, returned early, or was skipped by a conditional. Two mechanisms guarding the same boundary is deliberate, not redundant — this is the one boundary in the system where a single point of failure…
15. **Visual capture uses `chrome.tabs.captureVisibleTab`**
   — ARCHITECTURE.md Section 2.1 said "`chrome.tabCapture` or an in-page canvas snapshot" without choosing. `captureVisibleTab` is a better fit than either: it returns exactly one still image of the visible viewport, which is what PRD.md Section 20 specifies we process, whereas `tabCapture` yields a…
16. **No static `content_scripts` in the manifest — the content script is injected on demand via `chrome.scripting.executeScript` under `activeTab`**
   — A static content script matching `<all_urls>` would run on every page the user ever visits and require broad host permissions. On-demand injection means Shield has no presence at all on pages the user hasn't explicitly pointed it at.
17. **Build output is unminified**
   — Shield's core claim is that anyone can verify nothing unredacted is transmitted. Shipping minified code would undercut that at the moment it matters most — when a judge or reviewer opens the source.
18. **Vite build runs in two passes (`vite.config.ts` plus `vite.content.config.ts`)**
   — Content scripts execute in a classic, non-module script context and cannot use runtime `import`, so they must be a single self-contained bundle. The popup and service worker can be ES modules and benefit from shared chunks.
19. **Vite 8, not Vite 5**
   — Vite 5 pulls a transitive esbuild with a published advisory. The advisory only affects the dev server, which we never run, but the project has a dependency-scanning commitment in TECH_STACK.md and shipping a known-vulnerable toolchain would be a bad look in a security-focused submission.
20. **Extension icons are generated from source (`extension/tools/make-icons.mjs`, Node built-ins only) rather than committed as binaries**
   — Keeps the repository fully reviewable — there is no opaque image blob anyone has to take on trust — and adds no dependency. `public/icons/` is gitignored and regenerated by the build.
21. **`CapturedFrame` holds an `ImageBitmap`, never the `data:` URL that `captureVisibleTab` returns**
   — A base64 string of an unredacted screenshot is the most dangerous value in the extension — it can be console-logged, passed to `sendMessage`, or JSON-stringified by accident, and each of those is a leak.
22. **Frames are released explicitly via `disposeFrame()` in a `finally`, on every exit path from a run**
   — `ImageBitmap` pixels live outside the JS heap and are not collected promptly. PRD.md Section 16 promises captured frames are discarded immediately after processing, and an aborted run must not leave a screenshot resident.
23. **CSS-to-frame pixel scale is derived by measurement (`frame.width / viewport.width`), not taken from `devicePixelRatio`**
   — Scrollbar width, page zoom, and Chrome's own rounding all move the real ratio away from the reported DPR. Redaction rectangles come from DOM coordinates in CSS pixels, so a systematic scale error would offset every blur box on the frame — a redaction that misses its target is a leak, not a cosmetic…
24. **Capture format is PNG (lossless)**
   — The local vision model and any OCR pass read these pixels directly, and JPEG ringing around text is exactly the artefact that costs detection recall — weighted more heavily than latency in PRD.md Section 7.
25. **The screenshot data URL is decoded by hand rather than with `fetch(dataUrl)`**
   — `fetch` on a data URL is harmless in itself, but it means an unredacted screenshot briefly exists as a request. "No code path sends a frame anywhere before redaction" is a far easier claim to audit when the frame never touches a networking API at all.
26. **One automatic retry when `captureVisibleTab` hits Chrome's ~2-calls-per-second quota**
   — The multi-step task loop can legitimately capture faster than the quota allows. A transient throttle is not a failure the user should have to understand, so it is absorbed rather than surfaced. Genuine capture failures (chrome:// pages, PDFs, no activeTab grant) still surface with a specific…
27. **Every pipeline stage is timed against the ARCHITECTURE.md Section 6 budget from the start (`src/lib/timing.ts`), logging a warning when over budget**
   — Latency is 15% of the score, and it is lost not to one catastrophic stall but to a stage quietly drifting over budget across many commits. Timing with the budget written next to the measurement makes that drift visible the day it appears.
28. **The content script never reads the value of a password field — not read-then-redacted, never read at all**
   — Nothing downstream wants it. The Redaction Engine would replace it with `[PASSWORD]`, and API_SPEC.md Section 5 forbids the server from sending a sensitive value back, so the Action Executor never needs one either.
29. **Selectors are built from tag names plus `:nth-of-type`, preferring a unique `id`; class names are never used**
   — CSS-in-JS and utility frameworks regenerate class names between builds and sometimes between renders, so they look specific while being the least durable thing available. The Action Executor has to re-resolve the target after the page has had time to change (PRD.md FR-21), so durability beats…
30. **Every generated selector is verified to round-trip at capture time, and failures are counted**
   — A selector that cannot find its own element while that element is still in hand certainly will not find it later. Far better to know during the scan than to discover it while acting — acting on the wrong element is one of the failure modes PRD.md Section 20 explicitly calls out.
31. **Interactive elements (inputs, buttons) are collected before text and images, and are never dropped by the 300-element cap**
   — The cap exists to bound payload and latency on large pages. If something must be dropped it should be background prose, never the field or button the task depends on — dropping those would cost task accuracy, the heaviest single metric at 25%.
32. **Anchors with `href` are classified as `button`**
   — The API_SPEC.md Section 3 vocabulary has no "link", and from the reasoning model's point of view what matters is that it is a click target. Calling a "Forgot password?" link `other` would hide a legitimate next step during the exact task we care most about.
33. **An empty element map fails the run**
   — Zero elements is indistinguishable from a page with nothing sensitive on it, and the PII Detector would find nothing to hide and pass it straight through. Failing closed on an empty reading is required by ARCHITECTURE.md Section 9.
34. **The element map is logged to the service worker console without field values — labels, types and selectors only**
   — A console is somewhere content travels to: it survives in the devtools buffer and gets pasted into bug reports. Page structure is safe to show; what the user typed is not.
35. **`domScan` gets its own 100ms latency budget alongside `capture`**
   — ARCHITECTURE.md Section 6 has a single "Screen capture < 100ms" line, but Screen Perception is two independent pieces of work with different performance characteristics and different fixes when they get slow.
36. **The content script registers its message listener unconditionally, with no `window.__shieldLoaded`-style double-injection guard**
   — Such a flag lives on the page, which outlives the extension. After an extension reload every already-open tab still carries the flag, so the fresh injection skips registering while the previous script sits orphaned and unable to receive anything — leaving the tab permanently deaf until reloaded by…
37. **Every build stamps itself, and both the service worker and the content script log that stamp plus the manifest version on startup**
   — Chrome will happily keep running a previous build — a cached service worker, a second copy loaded from another folder, a reload that silently did not take. All of those look identical to "the code is broken" from the console, and three sessions were lost to exactly that ambiguity, including one…
38. **The popup displays the running version and build stamp in its footer**
   — The service worker DevTools console silently detaches when an extension reloads and then replays its old buffer indefinitely, which is indistinguishable from "the new code does not work". Several sessions were lost to that ambiguity.
39. **A `<label>` element is not reported as a standalone text region when its text is already carried as a control's `label`**
   — Without this every labelled field appears twice — once as the input carrying "Password", again as a text region saying "Password". On the login test screen that was 3 of 11 elements duplicated; on a signup form it is worse.
40. **The unresolved-selector count is logged even when it is zero**
   — It is a correctness check, and a check you only see when it fails is one you stop trusting. Seeing "0 unresolved selectors" is what makes its absence meaningful.
41. **The local vision layer targets what DOM cannot see — faces and text baked into pixels — rather than generic UI-element detection**  — **AMENDED BY 185** — whole-frame text regions are in scope; generic icon detection is not.
   — ARCHITECTURE.md Section 2.1 describes a model that "detects and classifies visual regions", but DECISIONS.md separately locks DOM as the primary signal, and the DOM walk now maps a login form completely in 3.9ms.
42. **Face detection uses UltraFace version-RFB-320, not BlazeFace**
   — Three reasons, in order of weight. (1) Fit: UltraFace is trained on WIDERFACE and built for "medium/long-distance small faces", which is our actual case — a profile photo or video-call thumbnail somewhere on a page.
43. **Local models are committed to the repo, pinned by sha256 in `extension/tools/models.json`, and verified on every build**
   — ARCHITECTURE.md Section 8 requires pinned models shipped with the extension. Fetching at build or run time would mean the demo can break because someone else's host changed a file or went down. A model is also the one artefact here that is downloaded rather than written, and a truncated or swapped…
44. **OCR runs only on crops of image elements, never the full frame**
   — Tesseract.js on a full 1920x945 frame would take hundreds of milliseconds to seconds and destroy the latency budget. But the DOM element map already tells us exactly where the `img`, `canvas` and `video` elements are — the only places text can hide from the DOM in the first place.
45. **Local inference runs in an offscreen document, not the service worker**
   — Not a preference — a hard constraint. Manifest V3 service workers disallow dynamic `import()` per the HTML spec, and ONNX Runtime Web's WASM and WebGPU backends are both unavailable there (microsoft/onnxruntime#20876).
46. **`CapturedFrame` (holding a decoded ImageBitmap) is replaced by `RawFrame` (holding the still-encoded data URL)**
   — The offscreen split above made the original design wrong. The service worker would have had to decode a frame only to re-encode it to cross the message boundary — slower, and it would have put raw pixels in the networking context for no benefit.
47. **ONNX Runtime's WASM assets are copied into the extension and loaded via `ort.env.wasm.wasmPaths`, never from a CDN**
   — Two reasons, the second decisive. A CDN fetch breaks offline, which during a live demo is plausible and unacceptable.    — Two reasons. Practically, Chrome's self-XSS guard blocks pasting into DevTools until the user types "allow pasting", which turned a one-line test into a support conversation — a test nobody can run easily is a test that does not get run.

   — The first version reported its verdict solely by pushing a message at the single moment the test finished, and cached whatever it got. That produced the one outcome a self-test must never produce: silence.

   — It is a property of the task loop, not of perception. The capture code it depends on is finished and verified, but nothing can trigger a second capture until the executor's loop exists, so the item could never be satisfied where it sat — leaving Module A permanently open on work belonging to…

   — SECURITY_PRIVACY.md Section 4 states that a missed detection is a more severe failure than an unnecessary one, so there is no confidence below which Shield decides to let something through. Storing a number invites a future `if (confidence > threshold)` around a redaction, which would quietly…
65. **Field rules apply only to value-holding controls; visible text is matched by content instead**
   — Field-name patterns describe what a control *holds*. Run over links and buttons they misread UI chrome as data — "Forgot password?" on the login test screen matches the password pattern perfectly and is not a password.
66. **Phone detection in visible text requires ten digits, or eight with an international prefix**
   — A flat eight-digit threshold cannot tell a phone number from a date range — "Copyright 2024-2025" is eight digits in two groups and matches the shape exactly. 67. **Fields are flagged whether or not they currently hold a value**
   — An empty password box is still a password box. The page can fill it between capture and transmission, which is the time-of-check-to-time-of-use gap the threat model's tampering row warns about.
68. **Face detection runs at a 0.5 score threshold, below UltraFace's usual 0.7, and every kept box is padded by 15%**
   — SECURITY_PRIVACY.md Section 4 asks for a bias toward over-redaction on faces specifically, and the asymmetry is stark: a false positive blurs a rectangle of background, a false negative puts someone's face on a server.
69. **Face boxes are carried as fractions of the frame, converted to CSS pixels in exactly one place**
   — Coordinate errors are the failure mode that matters for visual redaction, because a box offset by a systematic scale factor still looks like a plausible redaction while leaving the actual face visible.

   — The PNG decision above set its own revisit condition — a visually heavy page pushing a single cold capture over budget — and it fired exactly as written. A photo-heavy real page produced a 1511KB PNG in 349.7ms against a 100ms budget, 26 seconds after the previous capture, so Chrome's ~2/sec…

   — The element map was printed in full on every run, on the reasoning that labels are page structure rather than user input and are therefore safe to show. That reasoning was wrong. 72. **Face box coordinates are clamped on both edges and re-ordered after padding**
   — Padding clamped the far edge down to 1 while leaving a near edge above 1 untouched, which turned an out-of-range box inside out rather than rejecting it. The result was regions with negative width reaching the redaction stage — `-1814x401` among them.
73. **Added an `other` category, and unmatched fields holding content are redacted by default**
   — CLAUDE.md and SECURITY_PRIVACY.md Section 4 both require ambiguity to resolve toward hiding, and the code did the opposite: a field whose markup matched no rule was passed through untouched. Flagging it needs a category, and none of the existing seven honestly describes "we could not tell".
74. **Arbitrary personal names in page text are out of scope, and the limit is documented rather than half-solved**
   — A real social feed produced zero DOM detections while displaying many people's names, because they sat in link and button labels. Names cannot be recognised by pattern the way an email or a phone number can — telling a name from any other capitalised words needs a named-entity model.
75. **The OCR pass is deferred, explicitly**
   — It is the only Module B task the locked login demo never touches, and it adds a model download and an inference stage to a pipeline that Modules C, D and E have not yet been built against. Marked deferred rather than left unchecked so the distinction between "not done" and "decided against for now"…
76. **Sensitive regions are painted out with an opaque fill, not blurred**
   — Blur looks better in a demo and is the more common choice, which is exactly why it deserved scrutiny: it reduces information rather than removing it, and both blurred text and blurred faces have been recovered by published attacks.
77. **DOM detections are painted onto the frame too, not only faces**
   — A DOM detection means the value is also visible on screen. An email address in a text field is in the screenshot as surely as it is in the DOM, so replacing the DOM value with a token while shipping a picture of the same characters would defeat the whole exercise.
78. **The redacted frame is encoded as JPEG at quality 80**
   — A separate decision from the capture format, and a simpler one: this image is already redacted, so nothing sensitive can be recovered from it however it is compressed. Only payload size and the server model's ability to read the page remain, and quality 80 keeps text legible at a fraction of…
79. **`sealAsRedacted` is the single mint point for `Sanitized<T>`, and sealing verifies rather than assumes**
   — The seal symbol is declared but never exported, so only one function can construct the type — which makes the invariant greppable: searching the codebase for `sealAsRedacted` finds every point where something was declared safe to send, and there is exactly one, inside the Redaction Engine.
80. **Face boxes are decoded against a reconstructed prior grid**
   — The model does not emit rectangles. Its `boxes` output is SSD-style regression offsets relative to a fixed grid of prior boxes, and reading them as coordinates is meaningless — measured raw range on a real page was -4.268..3.368.
81. **The prior count is asserted rather than assumed**
   — The first prior grid produced 4400 instead of 4420, because the last detection head has three box sizes and I gave it two. Without the assertion every box would have decoded against the wrong anchor — producing confident detections in the wrong places, which is far harder to notice than a negative…
82. **The backend ships a rule-based reasoner that needs no model**
   — The free-tier model choice has been the oldest open blocker, and it was blocking work that did not actually depend on it. A rule-based path reads the redacted DOM summary, recognises a login form by its placeholder tokens, and returns the corresponding action — with no key, no network and no…
83. **The action carries a credential *reference*, never a credential**
   — The server has no access to the user's password and must never be sent one — that is the whole premise. But the action it returns has to be able to say "fill the password here".
84. **Backend dependencies pinned to releases with prebuilt wheels for the Python in use**
   — The first pins were current-looking versions whose pydantic-core had no Python 3.14 wheel, so pip fell back to building from source and needed a Rust toolchain. A backend that only installs on machines with Rust is a backend that fails on somebody else's laptop on demo morning.
85. **Selectors are absolute paths to the root, not truncated at eight levels**
   — The walk stopped after eight ancestors to keep selectors short. On a shallow page that is harmless; on a deeply nested application it produced not a shorter selector but a *different* one — a relative chain like `div > div > span > a` that `querySelector` resolves against the first such element…
86. **Shield stores no credentials, and refuses credential-fill requests**
   — The reasoner can ask for a saved credential by reference. Honouring it would mean keeping passwords in `chrome.storage.local`, in plaintext, readable by any code in this extension — on a project whose entire claim is that secrets stay protected.
87. **`filled` added to the redacted DOM summary**
   — A redacted field reads `[PASSWORD]` whether it is full or empty, because the token says what belongs there rather than what is there. That hid the distinction the assistant needs most: "this field needs filling" and "this form is ready to submit" are different situations requiring different…
88. **Host permissions are limited to the local backend**
   — MV3 blocks cross-origin fetch from a service worker without an explicit host permission, so the transport needed one.    — Measured on a live login page. One password field and one email field, both detected correctly, and the reasoner then announced "Sign-up form filled and consented. Submitting it." and chose the sign-up LINK as the control to click.

   — Every miss so far has been answered by widening a rule, and that has a ceiling. The rules cannot know that a number in a paragraph is a case reference somebody considers private, because nothing in the markup says so and nothing ever will.

   — the first version was a document-sized `position: absolute` layer appended to `<body>`, which is wrong on a large class of real pages. An absolutely positioned element resolves against its nearest POSITIONED ancestor, and plenty of sites set `body { position: relative }`.

118. **The rectangle being dragged is painted in viewport space, from corners held in document space**
   — reported as "marking area is not working properly". The stored mark was correct; the live preview was painted at its document coordinate on a surface anchored to the viewport, so on any scrolled page the rectangle drew a full scroll-height below the cursor.
119. **Every colour in the popup is a token defined in both themes**
   — not tidiness. The latency panel hardcoded slate greys chosen for a dark surface (`#cbd5e1` for labels, `#94a3b8` for values) and rendered them on the light background, so the entire timing breakdown was near-white text on white and could not be read at all in light mode.
120. **A checksum may only ever sharpen a label, never license a leak**
   — The obvious reading of "validate the Aadhaar" is to reject the ones that fail, and that is backwards. A twelve-digit number that fails Verhoeff is still a twelve-digit number on someone's screen — a test value, a typo, a mis-scan, or a real number this code is wrong about — and is exactly as sensitive as a valid one. It is redacted either way by the generic digit-run rule; the checksum decides only whether we can name it, and therefore what the placeholder and the trust overlay say. SECURITY_PRIVACY.md §4: uncertain means hide.
121. **Indian identifiers are wired into the classifier AND the scrubber, not just the classifier**
   — They are two separate paths over the same text: the classifier flags a field so its value is tokenised, the scrubber handles free text including labels. A format one path knows and the other does not is hidden in the value and transmitted in the label — the exact defect found on a real site, where an account address rode out inside a label no field rule could see.
122. **Card is matched before Aadhaar, and Aadhaar carries a trailing lookahead**
   — Caught by a test: the Aadhaar pattern matched the first twelve digits of a sixteen-digit card and claimed the span, so cards were labelled Aadhaar and never Luhn-checked. A card is the longer and therefore more specific claim on a run of digits, and needs thirteen digits minimum, so it can never swallow a bare Aadhaar.
123. **The logo is geometry in one module, and every surface is generated from it**
   — The mark appears in the toolbar icon (four PNG sizes), the popup header, and anything outside the extension. Drawing it three times means three things that drift, and a mark subtly different in the toolbar than in the popup looks like a defect in a product whose whole pitch is care. `tools/logo.mjs` holds the shapes once; the PNGs are rasterised from them and the SVGs emitted from them. It also preserves what the icon generator was written for — no opaque image blob in the repository that a reviewer has to take on trust.
124. **The popup inlines the mark with `currentColor`; the black and white SVGs are for everything else**
   — Inline SVG inherits the accent token and recolours with the theme, so the popup needs no second file and cannot show the wrong colourway. The two fixed-colour files exist for surfaces that cannot inherit a colour: the deck, print, the README.
125. **The eye and pupil are knockouts, not white fills**
   — Filled with the even-odd rule so they are genuine holes. A white fill would carry a background with it, and the mark has to sit on a dark toolbar and a light popup unchanged.
126. **`public/icons/*.svg` is committed while the PNGs stay ignored**
   — The ignore exists for generated binaries. An SVG is plain text, fully reviewable, and is what anything outside the extension actually uses, so ignoring it would mean the one artefact the team needs to hand around is the one not in the repository.
127. **The popup is a single committed dark theme, not a light and a dark one**
   — It owns its own window and never sits against the page, so it has no obligation to follow the browser colour scheme. Maintaining two themes is how the previous version shipped a latency panel as near-white text on a white ground: nobody was looking at both. One surface tuned once is the more honest engineering, and a deliberate dark identity is also what makes a tool read as a product rather than a template.
128. **Exactly one saturated element per view — the primary action**
   — Everything else is a hairline, a tint or a muted grey. Restraint everywhere else is what lets the CTA be obvious without having to shout; a surface where several things compete for attention has no hierarchy at all.
129. **No web fonts. Segoe UI Variable with a system fallback**
   — The CSP forbids remote stylesheets, and bundling a face would put a binary blob into a repository whose premise is that everything in it can be read. Segoe UI Variable is a modern optical-sized family already present on the target machines, so the typography improves at zero cost and zero network.
130. **The run indicator is indeterminate, never a percentage**
   — The stages vary by page, so a percentage would be an invented number, and this is the surface whose entire value is that nothing on it is invented. It exists because a status word alone cannot separate "working" from "stalled" at a glance.
131. **Observe-only is a switch, not a checkbox**
   — It is a mode the next run either is or is not in, and a switch states that. A tick box reads as one item in a list of options, which understates what it changes.
132. **OCR is never the only thing between the user and a leak**
   — The obvious build is "run OCR on every image and redact what it finds", which makes the whole protection contingent on an engine loading, a language model being present and a photograph being legible — and when any of those fails it fails silently, transmitting a photographed ID card while the console reports a clean run. Detection is therefore two stages: candidates chosen by geometry alone, which cannot fail, then reading, which improves precision. A failed read covers the candidate whole.
133. **`ok: false` and `ok: true, words: []` must never be conflated**
   — The first means the image was never examined and must be hidden; the second means it was read and is clean. Treating a failure as an empty read is the one bug in this path that would be a privacy failure rather than a broken feature, so per-crop results carry the distinction all the way from the engine to the region builder, and a reply that loses a crop counts as unread.
134. **Recognised text is judged by the same predicate as a form field**
   — `classifyTextContent`, already consulting the Indian identifier rules and the generic patterns. A second rule set for text that arrived as pixels would mean an Aadhaar is caught when typed and missed when photographed, purely because two lists drifted apart.
135. **Words are grouped into lines before they are judged**
   — An Aadhaar number prints as three groups of four digits and the engine reports them as three words; judged individually none of them matches anything. Without grouping, the most common document layout in the country produces no detection at all.
136. **A size floor is what makes the aggressive fallback affordable**
   — Redacting every image would work and would be useless: it leaves the reasoning model a page it cannot describe, and the product becomes a thorough way of breaking websites. An avatar cannot hold a readable Aadhaar number, so it is never a candidate and never blacked out.
137. **The OCR engine, core and language data are served from the extension**
   — Tesseract's defaults fetch all three from unpkg and jsdelivr at run time. Left alone this module would hand crops of a user's screen to an engine downloaded from a third party — the precise thing Shield exists to prevent, arrived at through a library default. The CSP blocks the remote fetch if a path is ever wrong, which is the backstop working as intended rather than a formality.
138. **Below the fold is a coverage gap, not a leak — and the difference decides how much risk is worth taking**
   — `dom-map.ts` filters the scan to the viewport and capture is `captureVisibleTab`, so off-screen content is never detected because it was never captured, and therefore never transmitted. Full-page capture would buy no privacy at all, only reach. Weighing it as though it closed a leak would have justified a far riskier change than the facts support.
139. **The coverage boundary is stated on every run, not only on tall pages**
   — A field with no box over it reads as "checked and safe" rather than "never looked at", which is the one misreading this whole surface exists to prevent. A warning that appears only when it is inconvenient is one nobody learns to look for, so a single-screen page gets a quiet confirmation and a tall one gets the limit, in the same place.
140. **Full-page scroll-and-stitch capture was considered and rejected**
   — Four costs, one of them disqualifying. `captureVisibleTab` is throttled to ~2/sec against a 150ms run; a tall RGBA bitmap runs to tens of megabytes held twice; the payload grows from 71KB to near a megabyte; and sticky headers repeat at every seam, so the stitched image shows content that never coexisted on screen. That last one is fatal on its own — that image is what the "What was sent?" panel presents as a faithful record, and a composite is not one.
141. **Scanning the whole page is a separate path from running, never a flag on one**
   — A run transmits a sanitized payload in order to act; a scan does neither. Sharing an entry point would put one boolean between "nothing leaves this machine" and "something does". `scanPage` reaches no transport at all, so the safety argument is structural rather than conditional — there is no branch to get wrong.
142. **The scan overlay is pinned to the document; the run overlay still is not**
   — Not an inconsistency but the same rule at two widths. The run overlay clears on scroll because it describes one viewport, and boxes that followed the content would look authoritative over material nothing examined. A scan examined the whole document, so pinning its boxes keeps the claim exactly as wide as the evidence behind it.
143. **A scan that stopped short draws the boundary on the page, not just in a summary**
   — Where examination ended is a fact about a place, and somebody scrolling past it needs to see it there. A popup line they closed two minutes ago cannot tell them, and a tidy count over a page half of which was never read is the "checked and safe" misreading again, at greater scale.
144. **A scan puts the page back where it found it, on every exit path including a cancelled one**
   — It moves someone else's page for several seconds. Ending somewhere they never scrolled to is a small rudeness with a large tell: it says the tool has decided the page belongs to it.
145. **The coverage line reports pixels, not elements**
   — It first led with a count of elements skipped for sitting outside the viewport, and on the page that mattered it read "0 elements outside it were not looked at" — while the Aadhaar number on a card that *started* inside the viewport and continued below it had never been captured at all. The count said nothing was missed at the exact moment something was. What is not examined is the part of the page that was never in a frame, so that is what the line says; the element count is a detail, printed only when there is one.
146. **The scan overlap is sized for an ID card, not a line of text**
   — Sized at first for a line, on the reasoning that half an Aadhaar number matches nothing. True, and not the binding constraint: an image is read as a single crop, so a 250px card straddling a stop boundary is clipped in the look above and clipped again in the look below, and neither crop contains it. A quarter of the viewport holds a card at the size one is usually rendered.
147. **An image clipped at every stop is reported as never read, not as clean**
   — Found by two consecutive scans of the same page disagreeing: two identifiers, then one. OCR truthfully reports no identifier in the half of a card it was handed, and nothing downstream can tell that apart from a clean image. Full visibility is now tracked across the whole walk — seen whole once is enough — and an image never seen whole, that nothing was read out of, is reported as a gap. An image that DID yield a reading is left alone; silence about an unread image is the danger, extra detail about a read one is only noise.
148. **The audit log carries no URL, and that cost is accepted deliberately**
   — It exists to be exported, and an export gets attached to a ticket and pasted into a chat. A URL alone identifies a person or an internal system, which is why `pageUrl` never reaches a payload either. Entries are therefore told apart by time and shape rather than by page. A log that is dangerous to share is one nobody shares, and then it has audited nothing.
149. **The audit log keeps counts; the payload inspector keeps bytes**
   — Two records answering different questions and neither replaceable by the other. "What was sent?" must be readable literally, so it holds a whole payload and is one pass deep. "Has this been protecting me all week?" needs every pass, and keeping every payload would put hundreds of kilobytes of redacted screenshot per run into storage forever — a liability rather than a feature.
150. **Regions are narrowed to an entry in one function, not at each call site**
   — A `SensitiveRegion` carries an `elementId` and a `position`, which describe this page at this moment and are useless in a log meant to be shared. A caller free to spread a region into an entry would eventually include them, so `buildAuditEntry` is the only thing that reads one and it keeps `category` and `reason` alone.
151. **The audit log is written after the send, and never awaited**
   — It records what a pass did, so writing it before the pass finished would be recording an intention. Not awaited because a storage write must never sit in the path of the run it describes; a failure is logged and dropped, exactly as `recordTransmission` handles its own.
152. **A scan's findings become redaction regions for every later run on that page**
   — Without this a scan is a pointing exercise. It walks the document, finds an Aadhaar number below the fold, draws a box on it, and then the next run reads one screen, cannot possibly rediscover it, and transmits the page. Detection that is not carried into the redaction is not protection. Findings are held in the content script in document coordinates, exactly as drawn marks are, and clipped to the viewport at capture time.
153. **Hiding the scan's boxes is not forgetting its findings**
   — The boxes must come down before any capture or they are baked into the frame the model is shown, and OCR reads Shield's own labels back as findings. The findings must not, or the protection ends the moment the explanation does. `SET_SCAN_VISIBLE` and `CLEAR_SCAN` are therefore different messages, mirroring the split that already exists for manual marks.
154. **A carried finding keeps its category and rule, and is not flattened to `other`**
   — The scan ran the same detectors a run does. It knows the thing it found was an Aadhaar number, and the manifest and the overlay should both say so; a manual mark is `other` because a person pointing at a rectangle has not told us what kind of thing it is, which is a different situation.
155. **A carried finding is a claim as of the moment the scan ran**
   — A page that reflows underneath these coordinates will drift, exactly as a drawn mark drifts, and a navigation destroys the content script and takes them with it. Drift over-redacts rather than under-redacts, which is the safe direction and why this is acceptable — but it is a limit, not a guarantee, and it is stated in SECURITY_PRIVACY.md rather than left for someone to find.
156. **The audit export is written in plain ASCII**
   — The first real export came back with the em dash in its note rendered as mojibake, in the one sentence whose job is to reassure a recipient that the file is safe to pass on. The file is opened by whatever the reader has to hand, not by us.
157. **A full-page image is never transmitted, because it would make the agent worse**
   — The decisive number is resolution, not latency. Vision APIs downscale to roughly 1500px on the longest side, so a five-screen page arrives about 600px wide and 16px text lands at ~5px, with form fields around 100px across. The model would receive the same page at a third of the detail it gets now. Latency, payload and stitch seams are all real costs on top; this one alone settles it.
158. **The whole page, redacted, is produced as PROOF and kept local**
   — What a full-page picture is genuinely good for is showing a person that every screen was examined and everything sensitive was covered. That job has no network in it, so the scan — which already walks every screen — redacts each one and keeps it. Free of every cost above, because nothing is transmitted.
159. **The record is a filmstrip, never a stitched image**
   — Sticky headers and fixed furniture repeat at every seam, so a joined page shows content that never coexisted on screen and repeats banners that appear once. This is the surface whose entire value is that it can be believed literally; a composite would be the one place in the product showing somebody a page that does not exist.
160. **A screen that could not be redacted is omitted and counted, never stored raw**
   — Storage outlives the tab, the browser and the session, so a raw frame written there is a screenshot of a private page left on disk — a far longer-lived exposure than anything else in this pipeline creates. The gap is declared in the caption instead, because a filmstrip with an unannounced hole is read as the whole page.
161. **The scan record opens in its own tab**
   — It is the one artefact meant to be looked at rather than glanced at. A 348px popup cannot show a screenshot at a size where somebody can check that their own ID number was really covered, which is the entire question it exists to answer.
162. **Regions are deduplicated after merging, with live detections winning**
   — A run detects the email field itself and also carries the same field forward from a scan, so the manifest arrived with eight entries describing five facts. Nothing was under-protected, but the manifest the model reads, the payload inspector and the audit log counts are all meant to be exact. The first region wins and this pass's own detections are passed first: a live detection carries the rule that actually fired, a carried one is a claim as of whenever the scan ran. Manual marks are never merged away — a person pointing at a rectangle is not making the same claim as a rule matching there.
163. **No screen is redacted until every screen has been read**
   — Found on the first real filmstrip: screen 1 showed the Aadhaar number in the clear. Each screen was being painted with the regions found AT that stop, but a scan discovers as it goes — the number was read at the second stop, and the first stop's picture, where the same card is fully visible, had already been written without it. That put a screenshot of an unredacted identifier into storage, from the feature whose entire purpose is proving the opposite. The raw frames are now held for the length of the walk and every screen is painted with everything the whole scan found. Data URLs are strings rather than decoded bitmaps, so twelve frames is under a megabyte held for the length of the scan, and none of it is stored or transmitted.
164. **Ground truth is labelled from the page, never from the detector output**
   — A corpus labelled from what the detector does scores 100% by construction and goes on scoring 100% through every regression. Several labels are therefore things the DOM path structurally cannot see — a password field with no attribute saying so, a name in prose, an identifier inside an image. They are labelled because they are sensitive, they lower the recall figure, and that figure is the honest one.
165. **Misses are named; over-flags are counted**
   — A false negative is a sensitive field that was transmitted; a false positive is a harmless field that was hidden, costing the model some context. The rubric counts both, SECURITY_PRIVACY.md says the first is worse, and default-to-hide is a deliberate trade of the second for the first. Two columns of one table would flatten a distinction the whole design rests on.
166. **Metric 3 is measured as three numbers, never one**
   — Coverage alone is gamed by a blanket blur, which scores 100%. Redaction precision — of everything covered, how much needed covering — is what the metric actually asks, and a blanket blur scores near zero there. The signed area ratio is the plain reading of the two together. All three are reported.
167. **The benchmark report is generated, not written**
   — `npm run benchmark` rewrites docs/BENCHMARK.md in full. A hand-copied figure is one refactor away from being a lie, and this is the one document whose entire purpose is being true.
168. **Corpus areas are summed, never averaged as per-page ratios**
   — The first implementation averaged the ratios and excluded any page whose coverage was zero, so a page where every field was missed dropped out of the denominator and made the score go UP. A benchmark that flatters itself is worse than no benchmark, because its output looks like evidence. Sixteen tests now exist for the instrument itself.
169. **An identifier whose checksum failed is named with its alternatives, not with whichever pattern ran first**
   — Screen 5 hid `Account 402711558903` correctly as an `id_number` and told the user it "matched Aadhaar number format". Twelve digits starting 4 fits the Aadhaar shape, Aadhaar is ordered ahead of `bank_account` because it is the more specific claim, and that ordering was reaching the trust overlay as though it were evidence. It is not: Verhoeff is what separates the two readings, and it had failed. A match now carries the other kinds whose pattern fits the whole of the same span and that no checksum ruled out, and the reason names them — "matched Aadhaar number or bank account number format". Verified matches carry none, because a passing checksum leaves one reading. Nothing about what is hidden changes, and neither does the Aadhaar rule: a failed checksum still redacts, still at unverified confidence. Only the sentence changes, on the one surface whose entire value is that it can be read literally.
170. **Whole-span only counts as a competing reading**
   — A sixteen-digit card contains a run of digits the bank account pattern matches, but a pattern that accounts for part of a span is not answering the same question — that overlap is what the claiming order already exists to resolve. Only a pattern fitting every character is offering a different answer. This is also why a 4-4-4 grouped twelve-digit number stays Aadhaar alone: the account pattern needs an unbroken run, so the formatting does real discriminating work.
171. **The element-map export carries values verbatim, and is therefore gated three ways rather than sanitised**
   — Sanitising was the first instinct and it is wrong here, because it would make the benchmark measure a detector on input the detector never sees. Verhoeff runs on the actual digits; the Aadhaar rule reads the leading digit; the phone rule counts them. Replace `402711558903` with a shape skeleton and every recall figure computed from that page is a fiction about a page that does not exist. A corpus is only evidence if it is the real input. So the values stay, and the risk is answered where it actually lives — in who can trigger the export and what they see before it exists. Three gates: it is compiled out of any build that does not set `SHIELD_DEV=1` (see 183 — the first attempt only hid it); it shows every value it is about to write and will not produce a file until that list has been looked at and confirmed; and it drops `pageUrl`, exactly as the audit log does and for the same reason. The remaining rule — capture from logged-out or synthetic-data pages — is a discipline rule, and it is stated as one rather than dressed up as a guarantee.

   — "Only export when logged out" is unenforceable and a heuristic for detecting a session fails open, which is worthless as a safety claim. 176. **Two systematic gaps the bigger corpus found, and they point in opposite directions**
   — Financial amounts are missed as text and over-flagged as fields. A balance, a premium or an income rendered in prose passes untouched, because no rule matches an amount; the same quantity in a form field is hidden by the default-to-hide rule, which fires on content matching nothing. 177. **Pixel truth is boxes on a document, in that document's own pixels, never in page coordinates**
   — An element label cannot express what is on a scanned card: the element is the whole card, so "sensitive" cannot tell covering the number apart from painting over the image, and that difference is the whole of metric 3. The boxes therefore live in the card's own frame. Keeping them there means no page layout has to be invented to say where a card sat, and a box is only ever compared against a detection produced in the same frame.
178. **A pixel match needs an IoU of 0.5, and one detection may claim one labelled region**
   — Any-overlap matching would let a single rectangle over a whole card count as having found every line printed on it, which is precisely the blanket-blur behaviour metric 3 exists to catch. Both halves are needed: the threshold stops the whole-card box, and one-to-one matching stops a merely large box claiming two lines at once.
179. **The pixel layer measures everything after the recognition engine, and says so**

What it does measure had no measurement at all: line grouping, the shared classifier, and box placement — the half that lives in this repository and where the adjacency bug would be. 184. **The capture panel injects the content script itself**
   — Shield declares no static content script; the service worker injects it under `activeTab` when a run, scan or mark starts, which is a real privacy property rather than a smaller permission warning. 185. **Decision 41 is amended, not reversed: the vision layer gains text regions from the whole frame, not generic icon detection**
   — 41 ruled out generic UI-element detection on the grounds that the DOM already maps a login form in under 4ms, which is still true and still the right reason to keep DOM primary. What 41 did not weigh is that metric 1 is 25% of the score, names "on-screen elements, text regions, and UI structure", and the problem statement is called On-device Visual Perception. The amendment takes the half of that sentence the DOM genuinely cannot answer — text regions — and leaves icon detection out. Text baked into a canvas, an iframe or a pasted screenshot is invisible to the DOM walk today, so this is not only a metric gap: it is content that reaches a capture unexamined, which is a leak path.
186. **OmniParser's icon detector was evaluated and rejected on licence, not on merit**
   — `icon_detect` is the obvious candidate: a YOLOv8 fine-tune with a published ONNX export at 3.34MB int8, 640x640, which would drop into the offscreen host beside UltraFace. It is AGPL-3.0, inherited from Ultralytics, and it is the one component of that pipeline that cannot be skipped. Adopting it would impose AGPL copyleft on an extension that has no LICENSE file yet, and `tools/models.json` already records a licence per model precisely because that is a fact worth pinning. The MIT-licensed replacement, `icon_detect_v3`, is a YOLOv9-E — the large variant, published in an unmerged pull request with no ONNX export, and far past a 1.1MB weight budget on a metric that scores resource use at 20%. Neither is viable now. Recorded so the next person does not re-derive it.
187. **Small VLMs in the browser were evaluated and rejected on shape, before size**
   — The problem statement names Transformers.js, and SmolVLM-256M and Florence-2 both run in a browser under WebGPU today, so the temptation is real. Producing one would mean asking a decoder to describe a screen and then trusting the description, which is strictly worse than reading the DOM. The weights are also two orders of magnitude beyond the current model, against a 20%-weighted resource metric and a 150ms pass. Size alone would settle it; the output shape settles it first.
188. **Full-frame reading belongs to the scan path, never to a run**
   — A run is budgeted at roughly 150ms end to end and OCR over a whole viewport is a different order of cost from OCR over a 320x200 crop. Putting it in the run path would trade 35% of the score (latency and resource) for part of 25%. The scan already walks the whole document, transmits nothing, and carries its findings into every later run on that page — decision 152 — so a scan that also reads the frame protects the run without slowing it. The split is the same one 141 draws: capability lives on the path that has time for it.
189. **The payload inspector keeps the frame it sent, and shows it in its own tab**
   — The inspector already answered "what left this machine" as readable JSON, and dropped the frame with a note saying it was omitted for length alone, being redacted and therefore safe. The scan record proves a scan; nothing proved a run. One frame is now kept beside the transmission and opened at full size, because 149's argument against storing frames is about keeping EVERY payload forever — one entry, overwritten each run, is bounded at a few hundred kilobytes.

   — The JSON is the evidence and the image is the demonstration, so they cannot fail together. If the write is rejected the transmission is stored again without the frame, and the panel simply offers no picture. Losing the record of what was sent in order to keep a screenshot would invert what this surface is for.
191. **The frame opens in an extension page rather than as a data URL**
   — Chrome refuses top-level navigation to `data:` URLs, and a blob URL minted in the popup dies when the popup closes, which is immediately. `sent/sent.html` reads the frame from storage and renders it, exactly as the scan record's page does. It is also the honest place for the caption: a picture of somebody's screen deserves a sentence saying what it is and that it is what was transmitted.
192. **What was sent and what was examined stay two separate pages**
   — The scan record answers "was the whole page looked at"; this answers "what left the machine on the last run". 149 already split these two records because neither replaces the other, and merging their pages would blur a distinction the trust surface depends on.
193. **The agreement rate is one comparison over the whole walk, not a sum of per-stop comparisons**
   — A scan's stops overlap deliberately, so that nothing falls between two screens. The first version compared each stop and added the columns up, which counts the same paragraph once per stop it appears in. The uneven part is worse than the inflation: a line clipped by the viewport edge at one stop and whole at the next is dom-only once and agreed once, so a single piece of screen produces two disagreements and an agreement, and the ratio stops being about the page at all. The readings are now placed in document coordinates, merged per reader, and compared once — which also resolves that edge case correctly rather than specially, because a line both readers read is agreement whether or not they happened to read it at the same stop. A test asserts a page walked in two steps scores what it scores in one.
194. **The sighting merge matches on exact text, where the reader comparison matches on containment**
   — `textMatches` is forgiving because two different readers legitimately disagree about a comma. One reader looking at the same thing twice should return the same string, so the merge demands it. Containment would additionally collapse a label into the container that holds it, and whether those are one piece of screen or two is a real question that a de-duplication pass has no business answering silently.
195. **The server model is Qwen2.5-VL-32B-Instruct, Apache 2.0, and the licence was the first filter**
   — The problem statement requires open weights, so the field is Qwen2.5-VL, InternVL3, Llama 4 multimodal, Pixtral and Molmo. 186 rejected OmniParser's icon detector over AGPL-3.0 inherited from Ultralytics, and applying a weaker standard on the server than on the client would make that entry a preference rather than a rule. Qwen2.5-VL-32B-Instruct is Apache 2.0, leads the open-weight field on OCR-heavy benchmarks, and is hosted free on OpenRouter — which speaks the same chat-completions shape the adapter already targets, so pinning it is configuration and not code.    — "Offline deployable" is in the problem statement, so it has to be more than a claim. `ollama pull qwen2.5vl:7b` is 6.0GB at Q4_K_M and serves an OpenAI-compatible endpoint the adapter reaches by changing one environment variable; vLLM serves the 32B unchanged on a machine that can hold it. What we will not do is imply one binary runs everywhere: the cloud demo runs the 32B and a laptop runs the 7B, same licence, same wire format, same prompt, smaller model. Ollama's 7B on CPU is roughly 3–8 tokens per second, which is usable for one action per screen and nothing faster — stated because a judge will ask and a vague answer is worse than a modest one.
197. **The redacted frame is attached by default, and a model that cannot see costs one request rather than the feature**
   — The frame was opt-in behind `SHIELD_MODEL_VISION`, on the reasoning that text-only free tiers are commoner and the DOM summary alone handles the form tasks in scope. Both were true and both answered the wrong question: the problem statement is about visual context reaching the reasoner, and a frame that is captured, redacted, sealed, verified and then left behind is the whole capability being built and not used. It is also the only artefact on the wire that demonstrates the redaction to the party it is for. Flipping the default cannot be allowed to break a working text-only configuration, so a 4xx on a request carrying an image is retried once without it, answers from the model anyway, and latches for the life of the process. A 4xx is now a distinct exception from an unusable answer, because it is the only failure worth retrying differently.

   — The prompt described a screenshot and its black rectangles in every request, while the adapter attached one only when vision was enabled. Nothing failed and nothing was logged; the model was simply told about a picture it had never been given, in the same message that tells it black rectangles mark hidden information. The with-frame text also names PAGE CONTEXT as authoritative for elementIds and the image as supplementary — the same division of labour the client uses, and the one that stops a model naming an element it can see but was never given.
199. **Two real values belonging to the operator were replaced with same-shape synthetics, which is not the masking 171 forbids**

Where digits genuinely carry information the replacement is generated against the project's own checksum code rather than invented. 202. **The Firefox port's three risks were researched before a line was written, and the largest one does not exist**
   — The worry that would have made this expensive is the namespace: every `await chrome.storage.local.set(...)` in this codebase assumes a promise, and Firefox historically gave promises on `browser.*` and callbacks on `chrome.*`. Under Manifest V3 Firefox returns promises from `chrome.*` too, so the client's API usage ports unchanged and no compatibility shim is needed. The second, that MV3 means service workers everywhere, is also false: Firefox MV3 runs an **event page**, which is a real DOM document. That inverts the expected difficulty — the offscreen document exists only because a Chrome service worker cannot host WebAssembly or WebGPU, so Firefox needs *less* machinery, not more. The third, WebGPU, is available by default from Firefox 141 on Windows and 145 on Apple Silicon, with Linux and Android still in progress; absence degrades to the WASM path this project already proves with a self-test, so it is a performance question rather than a blocker.
203. **Firefox is a separate build target whose manifest is generated from Chrome's, not a second hand-written file**
   — MDN's advice is to put `scripts` and `service_worker` in one `background` key and let each browser choose. That works and was not chosen, for one reason: it edits the file Chrome loads, and Chrome is the primary demo. `npm run build:firefox` copies `dist/` and rewrites only what the two browsers disagree about, so a build for one browser cannot break the other. Generated rather than committed because two hand-maintained manifests drift silently — a permission added for a Chrome feature simply never reaches Firefox, and the symptom appears as a runtime failure on the browser nobody tests daily. The deltas are four: an event page instead of a service worker, no `offscreen` permission, no `minimum_chrome_version`, and a `browser_specific_settings.gecko` block.
204. **The Firefox vision path is not built, and the absence says so rather than crashing**  — **SUPERSEDED BY 205.**
   — On Firefox the model should run in the background event page directly, which means extracting the offscreen document's message dispatcher into a function the background can call instead of message. That is a change to the hot path every run depends on, and it cannot be verified from here, so it is not being written blind alongside a Chrome build that works. What is in place is the honest failure: `ensureOffscreenDocument` reports that this browser has no offscreen documents and that the Firefox path is unbuilt, rather than dying on a property lookup with "cannot read properties of undefined" — which names the symptom and hides both the cause and the fact that the browser needs a different shape rather than a fix. Loading the generated build in Firefox now tells us which parts already work, which is worth more than predicting them.
205. **The Firefox vision host is the same page in a hidden iframe, which supersedes the plan in 204**  — **REVERTED BY 207** — it hangs the extension.
   — 204 said the event-page path was not being written blind, because the obvious design meant extracting the offscreen document's message dispatcher, moving roughly two hundred lines out of an entry point, and doing it to the code path every Chrome run depends on from a machine that cannot run Firefox. That reasoning stands; the design it assumed turned out to be avoidable. Firefox's event page is an ordinary document, so it can hold `offscreen.html` in a hidden iframe. An iframe is a separate browsing context, which is the whole point: `chrome.runtime.sendMessage` does not route a message back to the frame that sent it, so a direct function call would have been required — but it does deliver to a child frame, exactly as it delivers to an offscreen document. Every helper in `messages.ts` works unchanged and so does every line inside the host. No dispatcher was extracted and no vision code moved. The branch is chosen at runtime on whether `chrome.offscreen` exists rather than at build time, so both bundles carry both paths and Chrome's is the one that runs — which also means the Chrome behaviour is provably untouched rather than argued to be.
206. **The two browsers dispose of the vision host differently, and Firefox's way is worse**
   — The host closes itself after two minutes idle by calling `window.close()`, chosen in preference to the service worker doing it because an MV3 worker is evicted and cannot be relied on to run a timer. A script may only close a window it opened, so inside an iframe that call is a no-op. The first version of this entry said the frame is removed by `closeOffscreenDocument` at the end of a run; that was wrong, and checking found something worth knowing - **`closeOffscreenDocument` has no callers on either browser.** Chrome's design deliberately left disposal to the host's own timer, because an evicted MV3 service worker cannot be relied on to run one, so the function has been dead since it was written. The consequence is that on Firefox the host is resident for the life of the event page, holding a compiled 25MB WASM module and any GPU buffers. That is a real regression against the 20%-weighted resource metric on Firefox specifically, and a larger one than first recorded. Fixing it properly means the host telling the background it is idle instead of closing itself, which is a change to Chrome's path too and is not worth making before T2.2 says what it actually costs.
207. **The iframe vision host was built, tried on Firefox, and reverted — it hangs the extension**
   — 205 held the host page in a hidden iframe inside the event page, on the argument that an iframe is a separate browsing context so `chrome.runtime.sendMessage` reaches it exactly as it reaches an offscreen document. That argument was right and is not why this failed. A same-origin iframe shares an **event loop** with its parent, and `ort.env.wasm.numThreads = 1` means inference runs on the host document's main thread — so the WASM grind starves the event page, which is the context that has to receive the reply. Observed on Firefox 155: the run never completes, no further popup button responds, and the popup will not reopen; Firefox's own console reports `Content process isn't responsive` and DevTools refuses to attach, which is also why the background console could not be opened to debug it. Reverted rather than left in, because code that hangs the browser is worse than a browser that is politely unsupported. What the attempt established is still worth having: everything up to inference works on Firefox, and the missing piece is specifically a thread, not a context. A real Worker, or the dispatcher extraction 204 described, are the two shapes that would work.
208. **Firefox support is parked, not abandoned, and the boundary is written down**  — **SUPERSEDED BY 215** — Firefox is un-parked.
   — What works there is proven rather than assumed: the event page starts under `type: module`, `chrome.*` returns promises, the content script injects under `activeTab`, the DOM map reads a real page, the popup renders, capture produces a frame, and ONNX Runtime initialises. 209. **The extension reports its own JS heap and says plainly that this is the smaller half**
   — Metric 4 is 20% of the score and had no numbers at all. The temptation is to add `performance.memory` and call resource use measured, which would be worse than measuring nothing: that counter covers one context's JavaScript heap, and Shield's two largest costs - ONNX Runtime's WebAssembly linear memory, where the 26MB module and every tensor live, and WebGPU buffers - are both outside it, with no API that reports either to the page. So the figure is logged at the one moment it means something (the session is built, so this is the resident cost of having a model rather than of using one), the line it prints names what it excludes, and `sampleMemory` returns null rather than zero where the counter is absent, because a caller that cannot tell "not measured" from "measured as nothing" will publish the wrong one. The protocol is the deliverable that can be written without a machine; the numbers need two machines, one without a discrete GPU, and they stay empty until somebody has run it.
211. **The page-level agreement rate is printed at the end of a scan, because the per-stop lines cannot be added up**
   — Each stop already logs its own agreed / pixel-only / markup-only counts, and somebody reading a console will naturally sum them. That is exactly the mistake 193 exists to prevent: overlapping stops read the same text twice, and the columns inflate unevenly. Until now the merged figure existed only inside the scan record, which meant the number the rubric actually asks for could not be read while testing - so the first real measurement was taken from per-stop lines that do not answer the question. 212. **The frame is doubled before recognition, the cost lands on the scan path, and the ceiling is on pixels rather than on either dimension**
   — 188 put full-frame reading on the scan path and left the magnification unmade on purpose, because upscaling costs a canvas four times the area against a resource metric worth 20% and nobody could yet say what it bought. The measurement arrived: on a real page the engine read 16 of the 59 text items the DOM reported, missing roughly 73% of the text it was looking straight at, which is the ceiling on everything this layer can contribute to metric 1. Doubling is the cheapest remedy that moves the capital height the engine sees from about eleven pixels to about twenty-two, and a larger factor should follow a measurement rather than precede one - 18.6% page agreement is the before-figure and every screen-read line now names the magnification it used, because a later reading without it is not comparable to anything. The budget is 9 megapixels and the figure is deliberately not round: doubling a 1920x1080 frame needs 8.29MP, so a lower ceiling would clip the commonest viewport there is while claiming to bound the extreme case. Above it the factor tapers rather than being refused, and a source already past the ceiling is read whole - the ceiling bounds what we ADD, because downscaling to fit a budget would make the engine read less than it does today on the largest screens, silently. The arithmetic lives in `vision/recognition-scale.ts` with ten tests rather than inside `ocr.ts`, which needs a browser and a 2.7MB engine to run at all: every coordinate defect in this project has been a plausible number computed somewhere untested.

214. **Firefox is a supported target rather than a port, and decision 2 is superseded**
   — 2 chose Chrome only, and its stated reason was that it "simplifies the build significantly for a hackathon timeline". That reason described a cost nobody had measured yet, and the measurement went the other way: 202 established that the namespace risk does not exist, because Firefox returns promises from `chrome.*` under MV3 and the client ports unchanged; that Firefox MV3 runs an **event page**, which is a real DOM document, so it needs *less* machinery than Chrome rather than more; and that WebGPU is on by default from Firefox 141. 203 then built a generated manifest and `npm run build:firefox`, and a Firefox build loads and runs everything up to inference today. So the trade 2 described no longer exists — the build is already built, and what is left is one named defect rather than a second implementation. The problem statement also names the browsers explicitly ("popular browsers (chrome, Firefox)"), which makes this a compliance item and not a preference. **Chrome remains the primary demo and the reference implementation**: where the two browsers disagree, Chrome's behaviour is the one that is preserved, and a change that breaks Chrome to serve Firefox is not taken.
215. **Firefox is un-parked, and 208's arithmetic is restated rather than quietly dropped**
   — 208 parked Firefox on an explicit comparison, and the honest way to reverse it is to show that the comparison changed rather than that somebody changed their mind. It weighed "a threading redesign on a browser that is not the demo" against "T2.2 sitting at 20% of the score entirely unmeasured". Both sides have moved. T2.2 now has figures on a real machine — idle 8MB JS heap, run peak 19MB GPU, CPU never above 1.1%, scan footprint 217MB (docs/RESOURCES.md) — so the thing that was being protected has been done. And 207 narrowed the Firefox work from "unknown" to a single diagnosed defect with two named shapes that would fix it. Parking was the right call when it was made and is the wrong call now; 208 stays in the file with its reasoning intact, because a reader six months from now needs to know the port was deferred deliberately and not forgotten.
216. **Inference moves to a dedicated Worker on both browsers, and it does not land until Chrome is measured**  — **AMENDED BY 217 / SETTLED BY 218** — the "Chrome is untouched" claim was false; the gate is now met and Chrome keeps the document host.
   — 207 diagnosed the Firefox failure exactly: a same-origin iframe shares an **event loop** with its parent, and with `ort.env.wasm.numThreads = 1` the WASM grind starves the event page that has to receive the reply. It named two shapes that would work — a real Worker, or the dispatcher extraction 204 described. The Worker is chosen for two reasons. The dispatcher version unblocks the reply but still runs inference on the event page's own thread, so the extension freezes for the duration; and a Worker is the *same* answer on both browsers rather than a Firefox special case, which means one host owned by the offscreen document on Chrome and by the event page on Firefox, instead of two vision paths that drift. **The gate is Chrome, and it is empirical.** ONNX Runtime selects WebGPU today on integrated Intel graphics and inference costs 31.7ms there; whether it still selects WebGPU inside a worker is a question for a measurement, not for documentation, and 207 is the standing lesson about reasoning an architecture through without running it. So this change lands only with a before-and-after on the same machine, and **a silent drop to WASM on Chrome is a reason to abandon the shape, not to accept it** — 214 makes Chrome the implementation that gets preserved. 206's disposal defect is fixed inside the same change rather than after it, because the host's lifecycle moves with the host: `closeOffscreenDocument` has had no callers on either browser since it was written, and on Firefox nothing disposes of the vision host at all.

217. **A context declares which inference host it is, rather than detecting it — and 216's Chrome gate was answered by the bug that broke it**
   — 216 promised Chrome's default was provably untouched because the branch is taken at run time. It was not. `chooseHost` asked `chrome.offscreen !== undefined` from inside the **offscreen document**, and `chrome.offscreen` is the API for *creating* one: it is exposed to the service worker, not to the document it creates. So the probe ran in the one context that cannot answer it, read `undefined`, concluded the browser had no offscreen documents, and defaulted Chrome to the worker — from inside an offscreen document, which is the living proof of the opposite. The same expression is correct forty lines away in `background/offscreen.ts`, where it runs in the service worker; copying it across a context boundary is what broke it. The fix is not a better probe: a context knows what it is, so the offscreen document passes `'document'` because it *is* one and Firefox's event page will pass `'worker'` because there is nothing else for it to be. `defaultHostFor` stays, fed by `HAS_OFFSCREEN` where the API actually lives. The accident is worth recording too: because Chrome ran the worker path by default, the first real run *is* 216's gate, and it passed — WebGPU is selected inside the worker at 31.8ms against the 31.7ms document baseline, so the abandon condition did not trigger. A measurement obtained by accident is still a measurement, but it is only readable because the host is printed; had it been assumed, this would have shipped as a silent default change. `forcedHost` is now reported alongside `host` for that reason — a run that says `worker` with it null is the browser's own default and a finding, one with it set is somebody taking a measurement, and conflating the two is exactly how this stayed invisible.

218. **216's gate is met — WebGPU survives inside the worker — and Chrome nonetheless stays on the document host**
   — Measured on one machine (integrated Intel), build 2026-09-16 23:13:53, same page and same task each time. Model inference: **document 34.0ms, worker (forced) 37.8ms**, with an earlier unforced worker run at 31.8ms and the 14th's document figure at 31.7ms. **Every one of the four selected WebGPU.** 216's abandon condition was a *silent drop to WASM*, and it did not happen, so the shape is viable and Firefox proceeds. What cannot be claimed is that the worker is slower: the spread within the worker alone (31.8 to 37.8) is wider than the gap between the hosts, and n=1 per cell. What can be seen is a structural cost one level up — the whole `local inference` stage ran 51.2ms on the document against 73.7ms and 55.2ms on the worker, so the extra thread hop and its two transfers cost something real even when the model run does not. All of it sits inside a 500ms budget.
   **So Chrome keeps the document host, and this is a decision rather than an omission.** 216 framed the measurement as gating "the worker becoming Chrome's default", and the result answers that question with *no*: there is a small measurable cost and no benefit whatsoever on a browser that has offscreen documents. The worker exists because Firefox has no offscreen document and its event page cannot be starved (207); it was never a Chrome improvement. 214 makes Chrome the implementation that is preserved, and preserving it here costs nothing — both hosts ship in both bundles and the override stays, which is what made this comparison possible at all.

219. **The vision path is extracted from the offscreen document, and each browser's entry point supplies only the wiring**
   — This is the dispatcher extraction 204 described and 216 required. `offscreen/dispatch.ts` now holds what the host *does* — decode, detect, read, redact, self-test, warm, reload — as a plain async function over a message. `offscreen/offscreen.ts` is reduced to what is genuinely Chrome's: a `chrome.runtime` listener and the idle timer that closes a window, 1.8kB against the 86kB it used to be. `background/vision-host.ts` is the branch: on Chrome the helpers are `sendMessage` calls to the offscreen document, on Firefox they call the dispatcher **in-process**, because the event page is a real DOM document and is the host. One implementation, two callers, and the browsers differ in one file instead of throughout.
   **The dispatcher is imported dynamically, and that is load-bearing rather than tidy.** It reaches ONNX Runtime, and a Chrome MV3 service worker is precisely the context that cannot run ONNX Runtime — a static import would put ~94kB of engine into the one bundle with no possible use for it. Verified on the built output rather than asserted: `dist/service-worker.js` statically imports six chunks, none of them `dispatch` or `inference-session`, and holds `import("./chunks/dispatch.js")` as a genuine dynamic call behind `HAS_OFFSCREEN`. Chrome never evaluates it.
   **The seven offscreen helpers moved out of `lib/messages.ts` for the same reason.** That file is imported by the popup and the content script, so a routing branch living there would have dragged the engine into both. Each helper had exactly one caller — the service worker — so they belong in the background bundle where the branch belongs. The message *types* stay put, which is the part the other bundles actually use.
   **206's disposal defect is fixed here, as 216 said it had to be.** Chrome's offscreen document closes *itself* after 120s idle, taking the WASM module and GPU buffers with it. Firefox's event page cannot close itself — it is the extension — so it drops the *session* on the same timer instead, releasing the same 25MB module and the same GPU buffers while the page keeps running. Without it Firefox pinned all of it for the life of the browser session, against a metric worth 20%.
   **What is not established: none of this has been run on Firefox.** It type-checks, it builds, `dist-firefox/` carries every chunk and a manifest with an event-page background and no `offscreen` permission, and Chrome's own bundle graph is verified unchanged in shape. That is not the same as a run, and 207 is the standing lesson about exactly this gap — an architecture reasoned through and not executed hung the browser last time. The claim here is "built and ready to test", not "works on Firefox".

220. **Firefox runs the whole vision path, WebGPU and all — and WebGPU on Firefox is unusable at 35s of shader compilation**  — **AMENDED BY 222** — the 35s was one-time build under contention; steady-state inference is 228ms and WebGPU stays.
   — First Firefox execution, 2026-09-17, build 00:03:40, income-tax login. **Three things are now established that were open.** The event page hosts the vision path in-process and the dedicated Worker spawns and runs: the architecture of 219 works as built. ORT **selects WebGPU** there — `model init on webgpu in the worker` — which closes the question 208 could not answer, where every observed run fell back to single-threaded WASM and the reason was never captured because the console belonged to the process that had hung. And the event page **stayed responsive throughout**: the popup rendered and animated, DevTools attached, logs streamed. 207's hang did not recur. The Worker fixed precisely the thing it was built to fix, which is the first time that claim has been tested rather than argued.
   **And the cost makes it unusable as it stands.** `model init 35263ms on webgpu in the worker (budget 3000ms)`, of which `shader warm-up 34487ms` — the session build itself was under a second, so essentially all of it is WebGPU shader compilation. Against Chrome's ~1s for the same model on the same machine. A 35-second wait before the first frame is not a demo, and it is not a product.
   **The number is contaminated and must be retaken.** The same run exposed a race in `ensureFaceDetector`: it checked `if (engine && info)` and then awaited, with no latch, so the popup's PREPARE warm-up and the run itself both passed the check and both built — two Workers, two ORT sessions, two WebGPU device requests on one GPU, visible as two `shader warm-up` and two `model init` lines. Chrome hid this for months because its init is ~1s and the two calls rarely overlapped; a 35s init makes the overlap certain. Fixed with the same shared-promise latch `background/offscreen.ts` already used for document creation. So 35s is an upper bound measured under contention, not a clean figure.
   **The open question this leaves is which backend Firefox should default to**, and it is empirical in exactly the way 216's was: if WASM on Firefox initialises in ~1s and infers in a few hundred milliseconds, it is the better experience by a wide margin even though it is the slower engine, and "prefer WebGPU" stops being browser-independent. That is one `forceBackend` comparison away and must not be decided from this entry.

221. **The CPU self-test pins its own ORT runtime configuration, because a Worker is a different realm and a side effect does not cross it**
   — `runSelfTest` builds an independent WASM session and never set `ort.env.wasm.wasmPaths`. That worked for as long as the live session ran in the same context: both imported one `ort` module instance, so `configureRuntime` set `ort.env` once and the self-test inherited it. Moving inference into a Worker (216) ended that silently — the Worker configures its own copy of the module, and the host kept ORT's default, which resolves the loader relative to the importing script. Observed on Firefox 2026-09-17: **`CPU fallback BROKEN — no available backend found`**, reaching for `chunks/ort-wasm-simd-threaded.asyncify.mjs` when the file is at `ort/ort-wasm-simd-threaded.asyncify.mjs`. The irony is exact: the function's own docblock says it must prove the fallback can be built **from scratch** and that "reusing anything from the working path would prove less than nothing", and inheriting another module's global was the one way it was still doing that.
   **Why this was invisible on Chrome, and why that is the dangerous part.** Chrome defaults to the document host, where the live session and the self-test still share a realm, so the inheritance still works and the test still passes. It breaks on Chrome only under `forceInferenceHost: 'worker'` — and the verdict is *cached*, so a machine holding a "CPU fallback verified" record from before the Worker landed would keep reporting success for a path that no longer builds. A cached proof of something that has since stopped being true is worse than no proof.
   **What it costs, stated plainly: Firefox currently has no working CPU fallback**, which is PRD.md FR-27 and the standing judge question about machines without a GPU. `wasmPaths` now travels in `modelDescriptor()` beside the model URL, because where ORT's binaries live is one fact and two copies of it drift — which is how this happened.

222. **Firefox keeps WebGPU: the 35s was one-time build, not per-frame cost, and the steady state is 228ms**
   — 220 recorded WebGPU on Firefox as "unusable at 35s" and said the backend choice was one `forceBackend` comparison away. The comparison turned out not to be the question. Measured 2026-09-17, same session, run one then run two: **local inference 12023ms then 249ms**, with model inference itself at **228ms**. The seconds were session build and shader compilation, paid once while the session lives; the per-frame figure is 228ms against Chrome's 34ms — roughly 6.7x slower, and inside the 500ms budget with room to spare. End to end run two was **364ms**. So WebGPU stays on Firefox, and "prefer WebGPU, fall back to WASM" remains browser-independent after all. 220's alarm was correct to raise and wrong in its conclusion, which is what a contaminated first measurement does.
   **The CPU fallback is now proven on Firefox too** — 19ms inference, 272ms init, where the same run had reported `CPU fallback BROKEN` before 221 was fixed. FR-27 therefore has evidence on both browsers rather than an assurance on one, and the judge question about machines without a GPU is answered with a number taken on the machine in question.
   **What this surfaces instead is a disposal trade that is not Chrome's.** 219 gave the vision host a 120s idle release, correct on Chrome where rebuilding costs ~1s against a 20%-weighted resource metric. On Firefox rebuilding costs ~10s, so the same timer turns a two-minute pause in a demo into a ten-second stall. The window is deliberately NOT changed here: the right number depends on what a resident Firefox session actually costs, and nobody has run the task-manager protocol on Firefox. Choosing a timeout to protect a metric we have not measured on that browser would repeat the mistake 212 and 210 are both about.

223. **Metric 1's target is DOM coverage, not agreement — and agreement is not maximised at 100%**
   — Agreement counts text both readers saw. If it ever reached 100% the vision layer would be redundant, because its entire purpose is reading what markup cannot describe: text inside images, canvas, scanned documents. So the 22.8% is three rows that mean different things. **Agreed (18)** is corroboration. **Markup-only (39)** is the only failure row — text the engine looked straight at and could not read, and the one that must fall. **Pixel-only (22)** is the layer earning its place and should hold or rise. The figure we drive is therefore **DOM coverage — agreed ÷ DOM items, 18 of 57 = 31.6%**: of the text the markup reports, how much can the engine also read. Target 60–70%, at which agreement lands around 40–50%, and we stop there. Pushing agreement higher past that point would mean suppressing pixel-only findings, which is destroying the feature to flatter the metric. Agreement is still reported, beside coverage, never alone.

224. **Metric 2 trades precision for recall deliberately; symmetry is not the goal**
   — 83.5% / 83.5% reads as balance, and the balance is a defect rather than an achievement. A miss is a leak; an over-flag is an annoyance. CLAUDE.md's constraint is already "when uncertain, hide it", so **recall 90–95% at precision 78–82% is a better privacy posture than 83.5 / 83.5** and is what detector work tunes toward. It is also the scoring position: EVALUATION_CRITERIA.md names recall on sensitive data specifically. A change that raises precision by lowering recall is a regression here even when F1 improves.

225. **Redaction coverage is never quoted alone**
   — Coverage 60.4% is the most dangerous number in the project: roughly 40% of sensitive area stays visible. It is also the easiest to fake, because a blanket blur scores 100% coverage at near-zero precision — which is exactly the comparison the naive-baseline study exists to run. Coverage and precision are therefore always stated as a pair, in that order, and never separately in a slide, a README or an answer to a judge. The shape of the gap matters too: 83.5% recall by count against 60.4% coverage by area says the things being missed are the big ones — prose, statements and photographed documents, which is what all 28 misses are.

226. **Metrics 4 and 5 are finished as engineering; what is owed on them is evidence**
   — Scan peak ~285MB against the income-tax tab's own 290MB is already the line worth defending: Shield at its heaviest costs about what one ordinary web page costs. Latency is inside every stage budget on both browsers once warm. Neither is optimised further — CLAUDE.md's working priority is that latency is improved after correctness and never instead of it, and 65% of the score sits in metrics 1–3. What metric 4 still lacks is measurement, not performance: Firefox figures, the settled-after value on Chrome, and a second machine for contrast. Recording those closes the metric; tuning it does not.

227. **The scan path captures PNG; the run path stays JPEG. One constant, two budgets**  — **REVERTED BY 230** — measured, and lossless pixels changed the reading by nothing at all.
   — DECISIONS.md 29 chose PNG because the vision layer reads these pixels directly and JPEG ringing lands exactly on the high-contrast edges a glyph is made of. 70 reverted it on a real measurement: a photo-heavy page produced a 1511KB PNG in 349.7ms against a 100ms budget. **Both were right about their own path, and the revert was applied to a path that did not exist yet.** A scan scrolls the document, waits for it to settle and reads the whole frame with an OCR engine at 2.0x — a stop already costs roughly four seconds (212) — so 188's point that the scan path has seconds where the run path has 100ms decides this. `captureEncoding(purpose)` is a pure function with three tests precisely so that a future change to one path cannot quietly become a change to the other, which is how 29 and 70 ended up in tension in the first place.
   **This is built and not yet measured.** The reason to expect anything is that the engine currently misses roughly two thirds of the text the DOM reports (212), and doubling the resolution bought only four points of agreement — so resolution was *a* cause and not *the* cause, and lossless encoding is the next candidate on the same list. Whether it moves DOM coverage is a question for a browser, and 212's lesson is that the after-measurement is stated against the before-figure or not at all.

228. **A scan reads each image once, whole — never clipped, never twice**
   — Stops overlap by 25% so that nothing falls between two screens, which means a picture near a boundary was being sent to OCR at two or three consecutive stops for an identical answer. OCR is the most expensive thing a stop does. `candidatesToRead` now excludes two kinds of candidate and the distinction between them is the whole safety argument.
   **Already read whole** is a pure saving: the set holds only candidates whose crop covered the entire image *and* whose read succeeded. A failed read never enters it, so it is retried at the next stop, and "attempted" can never come to look like "read" — which would be the one bug here that is a privacy failure rather than a lost optimisation. There is a test for exactly that case.
   **Clipped at this stop** removes a partial reading, not a protection. A crop from this frame holds only the visible part, and reading half a card returns clean about the half it was given — the failure `fullyVisible`'s own comment describes, and the one that produced the defect in SESSION_LOG lesson 6. An image clipped at *every* stop therefore never enters the read set, and `unexaminedImages` covers it whole at full confidence, which is a stronger outcome than a half-read that found nothing. What is genuinely given up is explanation quality: such an image is reported as "contents unknown" rather than by the identifier a partial read might have named.
   **The run path is untouched.** A run reads one screen once and has no later stop at which to see a clipped image whole, so it still reads whatever the visible part yields. The skipping is passed in by the scan, not built into the detector.

229. **A scan is profiled with no budgets at all**
   — `timed()` measures a run against ARCHITECTURE.md Section 6 and warns when a stage exceeds its budget. Applying it to a scan would fire that warning on every stage of every stop, because those budgets describe one pass over one screen and a scan is twelve passes with an OCR engine at 2.0x. A warning that always fires is a warning nobody reads, and worse, it would imply the scan is failing a target it was never given. `lib/scan-timing.ts` therefore accumulates totals, call counts and per-call costs with no budget column: the question a scan has to answer is not "was this fast enough" but "where did the time go", which was blank until now and is what every decision about scan speed depends on.
   **Shares are taken against wall-clock, never against the sum of the stages, and the remainder is printed.** Renormalising to 100% would make a profile that accounts for a fifth of the scan look complete. This is SESSION_LOG lesson 12 applied before the fact rather than after it — the tests are written against the instrument, not against the scan, because an instrument nobody has checked produces output that looks like evidence.

230. **PNG on the scan path bought nothing, and the null is clean: the scan goes back to JPEG**
   — Measured 2026-09-20, income-tax login, two stops, the same page and geometry as the 22.8% run of DECISIONS.md 212, so the comparison is like for like. **The first stop returned a reading identical to the JPEG run, item for item: 12 agreed, 9 pixel-only, 35 markup-only, both times.** Not close — the same three integers. Lossless pixels do not change what this engine reads off this screen, and 29's ringing hypothesis, which 70 only ever reverted on latency grounds, is answered on its own terms for the first time.
   **The merged page figures moved down, and that is page variance rather than the encoding.** Agreement 22.8% → 20.3%, DOM coverage 31.6% → **28.1%** (16 of 57, against 18 of 57). All of the difference is in the second stop — 10/15/27 became 9/13/28 — while the first stop did not move by a single item. An encoding effect that appears at one stop and is exactly zero at another is not an encoding effect. What this actually measures is **the noise floor of a single-page agreement figure: about three points**, which is a more useful result than the one we went looking for, and it is the number every future "we improved metric 1" claim has to clear.
   **PNG was not expensive here, which is worth recording because it contradicts the expectation.** The frames were 112KB and 140KB — *smaller* than the 132–180KB JPEG q90 they replaced, because a logged-out government form is flat colour and text, which is what PNG is good at. Capture cost 54ms per stop against a 100ms budget it does not even have to meet. So 70's 1511KB/349.7ms figure was a photograph-heavy page, not PNG as such.
   **It is reverted anyway, and the reason is that there is no longer anything to pay for.** A scan holds every stop's frame until the walk ends (up to MAX_SCAN_STOPS of them) so that no screen is painted before every finding is known, and on a photo-heavy page 70's figure is what that array fills with — a memory cost against a metric worth 20%, for a recognition benefit now measured at zero. `captureEncoding` stays, with both branches equal on purpose: it is what made this experiment one constant rather than a refactor, it is what makes the re-test one constant if the engine is ever replaced, and it stops the equality reading as though nobody had considered the question. That is precisely how 29 and 70 came to disagree.
   **Where this leaves metric 1.** Markup-only is still 41 of 57 — the engine is looking straight at two thirds of the text the DOM reports and cannot read it. Resolution was tried (212, four points) and encoding has now been tried (zero). Neither is the cause, and the remaining candidate is the recognition engine itself rather than the pixels handed to it. Nothing further should be tried on the input.

231. **The scan's cost is whole-frame OCR and nothing else: 82% of it, in one stage**
   — First scan profile, 2026-09-20, income-tax login, 1333px page in two stops: **7.0s total, 3.5s per stop**, of which `screen text` is **5.7s — 82%, at 2.9s per stop**. Everything else is rounding: settle 914ms (13%, and it is our own 450ms constant), face inference 108ms, capture 108ms, the redacted record 68ms, the DOM walk 10ms, scrolling 1ms. Unaccounted time is 10ms, so the profile is 99.9% complete and can be read as one.
   **This retires the assumption behind the scan-speed work.** Tier 3 named image OCR as the thing to cut, on the reasoning that overlapping stops re-read the same pictures. The profile says `image OCR 0ms`: a logged-out login form has no image candidates at all, so 228's skipping did not fire on this page and is neither confirmed nor refuted by this run. It will matter on a page with documents on it. It is not where a scan's time goes on a page of text, and it would have been optimised on faith for as long as nobody measured.
   **The same stage is both the cost and the ceiling**, which is the part that decides what to do next. `screen text` at 2.9s per stop is the 82%, and the 41 markup-only items of 230 are the same Tesseract pass failing to read what it is shown. One component is simultaneously the largest latency item in the scan and the binding constraint on a metric worth 25%. Work aimed at it counts twice; work aimed at anything else in this profile cannot pay, because the whole remainder is 18% of a path that transmits nothing and has seconds to spend (188).

232. **Shield is measured against four strategies it could have been, and two of them beat it on a headline number**
   — 225 made "coverage is never quoted alone" a rule, which left it depending on somebody remembering to say the caveat. `lib/benchmark/baselines.ts` replaces the caveat with a table: the same corpus, scored through the same `scorePage`, against **no redaction**, **blanket blur**, **hide every field** and **hide every value**. Generated by `npm run benchmark` into docs/BENCHMARK.md, never hand-written, for the reason every other figure in that file is.
   **The baselines are not straw men, and the test suite asserts that they are not.** `tests/baselines.test.ts` contains an assertion that blanket blur beats Shield on coverage — on purpose. If a change ever makes Shield win every column, the baselines have been weakened and the artefact is worthless; the test is there to fail when that happens. This is the same instinct as SESSION_LOG lesson 12, applied to a persuasion artefact, which is where it matters most because this table exists to be quoted at judges.
   **What it actually shows.** Blanket blur takes **100% recall and 100% coverage** — a perfect score on metric 3 read alone — by painting **3.04x** the area that needed painting, at **32.9%** redaction precision, and destroying **891 of 891** non-sensitive elements. Hide-every-value takes **94.1% recall, better than Shield's 83.5%**, and pays 28.8% precision and 55.6% of the page for it. Hide-every-field is the only naive strategy Shield beats outright, on every column. **Shield is the only row above 80% on recall, precision and redaction precision at once, while keeping 96.9% of the page readable.**
   **The column that does the work is `Context kept`** — non-sensitive elements still readable afterwards. It is the only measure here under which hiding everything scores zero, and it is the answer to the question no detection metric asks: can the agent still act on what is left. A redactor that hides everything has not solved the problem, it has moved it, from "the model sees private data" to "the model sees nothing". It is counted over elements rather than area because what an agent needs is the field, the button and the heading, not a percentage of the screen, and it is counted independently of `overFlagged` rather than derived from it — the two coincide for every strategy but Shield, and deriving one would make the column a restatement rather than a measurement.
   **It also prices the recall gap honestly, which is the part not to quote selectively.** Hide-every-value reaching 94.1% recall says the ~11 points Shield is missing are *reachable* — by aggression, at a cost of 55 points of precision and nearly half the page. 224's target of recall 90–95% at precision 78–82% is therefore a real frontier rather than a comfortable one, and the way to it is better detection, not a looser rule.

233. **The latency/accuracy study sweeps the two knobs Shield has, not the one the shape of the question suggests**
   — The PS asks for the balance explicitly and the obvious study is a confidence threshold against recall. **Shield has no such threshold, and adding one to produce a curve would be a policy violation rather than an optimisation.** `dom-rules.ts` says so in its own header — everything flagged is redacted whatever its confidence, because SECURITY_PRIVACY.md Section 4 holds a miss to be the more severe failure — and a curve swept over a knob the product does not have is a fiction however good it looks on a slide. The honest answer is to report the two knobs that do exist.
   **Knob one: which layers run**, in `lib/benchmark/tradeoff.ts`. The span is three orders of magnitude and that is the finding. The DOM walk owns **160 of the 170 labels and costs 4.4ms**. Face detection owns 3 and costs 34ms. Whole-frame recognition costs **2900ms per stop and owns none of them** — its output is measured as agreement against the DOM (metric 1), not as recall against labels, and crediting it here would hand it finds the DOM path is making, counting metric 1 twice under two names. **This is the quantitative case for 188's split between the run and scan paths**: a 150ms run cannot afford the layer that reads a canvas, and a path that transmits nothing can.
   **Every cost is quoted from a recorded run with its source printed, and an unmeasured one stays null.** Node cannot execute ONNX or Tesseract, so a figure this module produced itself would be a guess wearing a measurement's clothes. Image OCR has never been isolated on a real page — 231's profile read 0ms because that page had no image candidates — so its cell reads *unmeasured*, the cumulative column stops accumulating at it rather than producing a total that looks complete with a term missing, and `found` reads *needs a browser* rather than 0. A zero in a cost column reads as "free" and a zero in a found column reads as "broken"; both are confident claims about something nobody has run.
   **Knob two: the image candidate size floor**, which is a real latency/accuracy curve in one variable — lower it and more pictures go to OCR, buying recall on small documents and costing precision and one crop of latency each. **The shipped 140x80 turns out to sit exactly on the knee, and this is the first evidence of it.** Below it, recall holds flat at 90% all the way down to 40px while precision collapses 69.2% → 27.3% and the crop count rises to 2.54x: pure cost, no gain. Above it, recall falls immediately, 90% → 80% → 70%. The floor was originally derived from the width a twelve-digit Aadhaar number needs to stay legible — a derivation, not a measurement — and it survives being measured, which is a different claim and the reason the sweep was worth running.
   **The sweep goes through the shipped `imageCandidates` with its floor passed in as a parameter**, never through a copy of its geometry, and a test asserts an image that only appears at a loosened floor does appear. A sweep over a reimplementation measures the reimplementation, and would go on reporting a comfortable knee long after the real rule had moved.

234. **FR-14's range only goes up. `standard` is the floor of the setting, not its middle**
   — "Configurable redaction aggressiveness" reads as a slider with a lax end, and building one would violate two rules that are not negotiable: CLAUDE.md's constraint that when it is uncertain whether something is sensitive it is hidden, and `dom-rules.ts`'s rule that confidence never gates redaction. A level that let an identified password through, or that stopped hiding a field nobody could classify, breaks both. **So the setting cannot go below today's behaviour, and the honest answer to "can a user reduce redaction?" is no** — with a reason that can be pointed at rather than asserted.
   **What is left to configure is the part that was always a judgement call**: the GEOMETRIC floor for which pictures are worth reading. That is not a confidence cutoff and moving it cannot expose something a rule identified — the worst it can do is read more images. `standard` 140x80, `thorough` 100x57, `maximum` 40x23, and **every one of those is a row from the sweep in docs/BENCHMARK.md** (233) rather than a round number: 1.00x / 1.23x / 2.54x the OCR crops, at 69.2% / 56.3% / 27.3% precision. A test pins the three pairs to that sweep, so a floor edited without re-running the measurement fails rather than quietly shipping a guess.
   **`thorough` buys nothing on the current corpus and is offered anyway, which is stated rather than hidden.** Below 140 recall is flat at 90% on 50 pages — but 50 pages is not the world, and a document smaller than any we have labelled is exactly what a level above the default is for. Offering it with its measured cost printed is more useful than either omitting it or implying it finds more.
   **Every failure direction lands on `standard` or above.** An unrecognised value, a corrupted one, a missing key, a non-string, and a caller that forgets the argument all resolve to `standard` — the parameter on `ocrImageRegions` is defaulted for exactly that reason. There is a test for each, because a setting whose broken state loosens redaction would be worse than no setting.
   **One incidental fix.** `runStep` read settings twice — once for detection and once for transport, on either side of several awaits. A setting changed in between would have produced a step that detected at one level and reported another, which is a lie told by an await boundary. It now reads once per step.

235. **The browser-dependent work gets a runbook of its own, because "what is next" and "how to run it" are different questions**
   — TASKS.md says what is next and why it is weighted the way it is; GENERALISATION.md and RESOURCES.md each hold one protocol in full. Nothing said, in one place, which of the remaining items need a human and what the steps are — so the answer was being reconstructed in conversation each time, which is how a step gets dropped silently. docs/OPERATOR_RUNBOOK.md groups the eleven operator items into five sittings, gives the commands, and names the exact console lines to bring back.
   **It is explicitly subordinate to the two protocols rather than a third copy of them.** Where it disagrees with GENERALISATION.md or RESOURCES.md, the protocol wins and the runbook is wrong, and it says so at the top. A runbook that quietly forked a protocol would produce readings nobody could compare — which is the failure both of those files were written to prevent.
   **Session A merges three open items that were being planned as two sittings.** The sweep's results table already carries an Agreement column, so the twenty sites produce metric 1's missing pages as a by-product; there was never a separate "nine pages" exercise to run. The nine it names are chosen to vary **rendering** — canvas, Devanagari, dense small text, late-rendering SPA, text in images, dark low-contrast, iframe, serif — rather than to vary what PII they hold. Twelve captured corpus pages are all flat HTML forms in 14–16px sans-serif, and nine more of those would be nine correlated readings of a metric that is about whether the engine can read what the markup reports.

236. **Metric 1 on ten pages: DOM coverage is 22.2%, not 31.6%. The single page was flattering by nine points**
   — Nine pages scanned 2026-09-20, chosen to vary rendering rather than PII (235), pooled with the income-tax login: **762 agreed, 709 pixel-only, 2678 markup-only — agreement 18.4%, DOM coverage 22.2%.** Against the one-page figure of 31.6% that 25% of the score had been resting on. This is SESSION_LOG lesson 7 repeating exactly: four corpus pages scored 89.5% recall and thirty-eight scored 81.3%, and the drop was not a regression but the first honest look. So is this one.
   **The pooled figure is not an artefact of one enormous page.** Per-page coverage runs 8.5% to 37.4% — a **4.4x spread** — with a median of 21.6% that agrees with the pooled 22.2% to within a point. Two independent aggregations landing in the same place is what makes the number quotable. Summing across pages is legitimate where summing across stops is not (193): stops overlap by design, pages do not.
   **The spread is the finding, not the average.** A one-page figure was never going to be a rate, and 230 had already put its noise floor at about three points — the real page-to-page variation is more than ten times that. Anything that quotes a single page's metric 1, in either direction, is quoting noise.
   **Three predictions written before the runs, and the scoring is two right, two wrong, one half.** Right: Google Maps is overwhelmingly pixel-only (4 agreed against 42 pixel-only, the most extreme ratio on the list) and NSE's dense numerals are the worst read (785 markup-only). Wrong: GitHub's dark low-contrast theme was predicted to hurt and is the **best** page at 37.4% — dark is high contrast, and monospace suits the engine; and Apple's large display type was predicted to read near-perfectly and lands mid-table at 18.6%, because its text is mostly baked into images. Half: the Devanagari page's agreed count was near-zero as predicted, and its pixel-only count was 143, which the entry below is about.
   **Where this leaves the target.** 60–70% coverage (223) was set against a 31.6% baseline. The real baseline is 22.2%, the input has been exhausted as a lever (212 resolution, 230 encoding), and the remaining candidate is the recognition engine. The target is not restated here on the strength of one day's measurement, but it is now known to be further away than it looked.

237. **Two limits the sweep found that no test could have, and one it confirmed**
   — **A non-Latin page's pixel-only count is not evidence.** india.gov.in/hi returned 143 pixel-only regions with only `eng.traineddata` shipped: Latin-shaped guesses at Devanagari glyphs. It fails towards over-redaction, because pixel-only text becomes a scan finding and is hidden — safe, and the safe direction is not the same as a correct one. It inflates precisely the column 223 uses to argue the pixel layer earns its place, so **any pixel-only figure taken on a non-Latin page must be excluded from that argument**. Shipping a second language model is a size decision nobody has taken and it is not taken here. The related limit already recorded in GENERALISATION.md §1 was about English submit wording on the rule path; this is a different and larger one, on the vision path, worth 25% rather than affecting whether a click happens.
   — **`MAX_SCAN_STOPS` has now actually bitten a real page.** mygov.in is 15950px and the scan examined 8744 of them, 55%, then said so: `capped, the page continues past the last one`, `stopped early`, and a finding count stated against examined height rather than document height. The cap was a precaution for two years and this is the first time it has mattered. It is left at 12 — the honest partial answer is the design (24) — but "a long page gets a partial answer" is now a measured statement rather than a hypothetical one.
   — **231's profile holds across nine more pages, and the scan-speed change is confirmed firing.** Whole-frame OCR is 49% to 90% of a scan's wall-clock on every page measured, around 72% on average, with settle a steady 8–10% and everything else inside 5%. And `OCR: 4/4 image(s) read (2 skipped — already read whole or clipped)` appears repeatedly, alongside `0/n image(s) read at this stop` where every candidate was already covered — so 228's skipping works on real pages, which the income-tax login could never have shown because it has no images at all.

238. **The whole frame is read as sparse text; a crop keeps page layout analysis**
   — Metric 1 has exactly one failing row and it is markup-only: text the engine is looking straight at and cannot read, **2678 items against 762 agreed over ten pages** (236). Two hypotheses have now been tested and neither was the cause. Resolution bought four points (212); lossless encoding bought exactly zero, measured to the item (230). Both were about the PIXELS handed to the engine, and **the pixels are exhausted as a lever**.
   **What has never been examined is what the engine is TOLD.** Tesseract defaults to `tessedit_pageseg_mode` 3 — fully automatic page layout analysis, looking for columns, paragraphs and a reading order, because it was built for scanned documents and a scanned document has those. A browser viewport does not: it is a navigation bar, some buttons, a form, a footer and a heading off to one side — scattered short runs of text with no column structure worth recovering. Asked to find a page layout in that, the analyser groups unrelated regions and **discards some as non-text before recognition ever runs**, which is a mechanism that produces exactly the symptom observed. PSM 11, "sparse text, find as much text as possible in no particular order", exists for this case.
   **The two paths get different answers, and that is the whole reason this is a module.** A crop of a photographed ID card genuinely IS a document — a block of related lines in reading order — and PSM 3 is correct for it. Only the whole-frame path is a UI screenshot. Changing both would conflate two questions and put metric 3's pixel figures at risk while chasing metric 1, so `readCrop` defaults to `crop` and only `readScreen` asks for `screen`.
   **What is claimed: a plausible mechanism and the parameter Tesseract offers for it. Not that it will work.** 230 is the standing lesson — the encoding hypothesis was at least as reasonable and its effect was zero to the item. `lib/vision/segmentation.ts` is pure and separately tested for the same reason `recognition-scale.ts` is: it is load-bearing on 25% of the score and should not be the one part of the change nobody can check. The engine's nominal `PSM` enum cannot be imported there — it must run under Node — so the cast lives at the engine boundary in `ocr.ts`, and a test pins the values to '3' and '11' to keep the two in step.
   **The measurement that decides it is DOM coverage over the same ten pages, against 22.2%** — not against the 31.6% one page used to claim, and not on one page, whose noise floor is three points (230) against a real page-to-page spread of 4.4x (236).

239. **A scan prints what it found, not only how many**
   — The run path has printed a per-detection `console.table` since Module B. The scan path never has, so the path whose entire purpose is answering "what is on ALL of this page" could report `29 finding(s)` and nothing about what any of them were. That is how the generalisation sweep's Detect column turned out to be unfillable from a console: the operator could see the counts and not the findings. Positions are printed in DOCUMENT coordinates, because a scan's findings outlive the scroll position they were found at and a viewport figure would point at the wrong place on every stop but one.

240. **Consent before transmission fails closed, and is off by default — both stated rather than implied**
   — The payload inspector already shows the exact bytes that left, recorded before the request so it survives a network failure. It is the strongest evidence Shield has and it is evidence about something that has already happened: a user who disagrees with what was sent finds out afterwards. The consent gate is the same information one moment earlier, with a decision attached.
   **Exactly one outcome transmits.** A decline, a timeout, a popup closed mid-decision, a malformed reply and an approval arriving for a step that has already passed all resolve to not sending, and `mayTransmit` is the single place that says so. A gate that transmits when it is confused is worse than no gate, because it manufactures the appearance of a control that is not there — and a control that works only when nothing unusual happens is the kind of guarantee SECURITY_PRIVACY.md Section 4 forbids claiming. A stale id is refused rather than tolerated: an approval for step 1, clicked late, would otherwise authorise step 2's payload, which the user never saw.
   **Off by default, and the reason is not timidity.** Shield's invariant is enforced by a phantom type, a stage-order guard and a zero-leak content sweep — three mechanisms that ask nobody's permission. Consent is not what makes Shield safe, and shipping it on would imply it was. Defaulting it on would also put a modal in front of every step of a multi-step task, which is how people learn to click through consent dialogs without reading them: the failure mode every such dialog on the web already has. It is for the user who wants to see each payload before it goes.
   **The summary carries counts and categories, never values.** The inspector is one click away and is already a safe renderer of transmitted data; duplicating it here would create a second one, and the second is where the mistake would live. Placeholders are counted from the redaction manifest rather than by looking for bracketed strings in values, so a page whose own text contains `[EMAIL]` cannot inflate the number the user is shown — there is a test for that specific spoof.

241. **React and Tailwind, for the popup and nothing else**
   — The popup was 864 lines holding **39 imperative DOM handles**, several of them read and written from three places, with `render()` reaching into elements that other handlers had already mutated. That is the shape a declarative renderer removes rather than tidies, and it is the one surface a person actually looks at. Nothing else in the extension gains: the service worker has no DOM, the content script draws overlay rectangles at computed coordinates, and the offscreen document has no UI at all.
   **Neither dependency reaches the pipeline**, which is the only reason this was safe to do four days before a demo. Detection, redaction, the seal and transport are untouched; `dist/service-worker.js` contains no React, verified by grep rather than by reasoning about the bundle graph. The popup grew from 19kB to 579kB, which is a local file loaded from disk with no network involved.
   **DECISIONS.md 29 is not contradicted, and the distinction is worth stating** because it looks like one. 29 forbids building selectors from class names on TARGET pages, precisely because utility frameworks regenerate class names between builds. That is about pages Shield acts on. Shield never generates a selector for its own interface, so Tailwind inside the popup is outside 29's scope — and the rule that made us wary of utility classes is the same observation that makes them safe here.
   **What was NOT done, deliberately.** `proof/` and `sent/` keep their hand-written CSS. They are read once each, they work, and rewriting them would spend demo-week risk on surfaces nobody is looking at. `popup-legacy.html` is kept beside the new one so the old interface is one manifest line away if the new one fails in front of judges.
   **One defect this surfaced immediately.** `tsconfig.json` included `src/**/*.ts` and not `.tsx`, so the first build typechecked none of the new code while reporting success. Fixed, and it found two real bugs on the first honest run — including `scan.counts` being read as a record when it is an array, which would have rendered every bar as `NaN`. A check that passes because it is not looking is worse than no check.

242. **The popup is designed as a redacted document**  — **SUPERSEDED BY 243** — a specific reference interface was supplied, and a named reference beats a derivation.
   — The previous theme was a near-black ground with a blue accent: competent, tokenised, contrast-checked, and indistinguishable from every other developer-tool popup. Shield's subject is redaction, and redaction already has a visual language older than software — the opaque bar struck through a page before release. The interface is now built as the thing it does.
   **The bars are measurements, not decoration.** One bar per category actually found, width proportional to its share, floored so the rarest category stays visible rather than becoming a speck. A view with nothing hidden has no bars. If the widths ever stop being the data the bars should be deleted rather than kept for the look of them — a plausible rectangle that means nothing is the single failure mode this project has hit most often (SESSION_LOG lesson 1).
   **Black is `#000`, and that is semantic rather than stylistic.** A redaction bar that is merely very dark is one you can imagine seeing through. Body text sits lighter than the bars deliberately, so the bars read as absolute against it — the one place in this palette where maximum contrast is the message rather than a legibility setting.
   **Light, reversing the old theme's reasoning.** That reasoning — the popup owns its window and owes the page nothing — was sound and is outweighed twice: a bar needs a ground to be struck through, and on near-black it is a hole rather than a mark; and this gets demonstrated on a projector, where a light ground survives a badly calibrated beam.
   **Type is Bahnschrift**, a DIN-derived variable family shipping with Windows, which is the demo machine, falling back through the platform stack elsewhere. DIN is the type of instrument panels and technical drawings and this interface is mostly labels and measurements, so it is doing work rather than being a flavour. No web fonts: the CSP forbids remote stylesheets and bundling a face would put a binary blob into a repository whose premise is that everything in it can be read.

243. **The popup follows a supplied reference interface, and the bars survive it by inverting**
   — 242 reasoned the design from the subject: redaction is a black bar struck through a page, so the interface became a light document with things blacked out. That was a defensible place to arrive from the brief alone. **The brief is no longer alone.** A specific extension UI was supplied as the target, and a named reference beats a derivation every time — the person holding it can see something about the audience that the derivation cannot.
   **Five things are taken as a system rather than sampled.** A blue-black ground, not neutral grey and not pure black, with cards one step lighter separated by hairlines and no shadows anywhere. Radii that step down with nesting: window, card, control. **Tabs that protrude from a card's top edge** rather than sitting inside it — the detail that makes the reference recognisable and the easiest to leave out, and the reason no card in this tree may clip its overflow. **Exactly one holographic gradient, on exactly one control per view**; a second anywhere would spend what makes the first work, so it lives in a single `.key-fill` class rather than as a repeated Tailwind arbitrary value. And a violet stripe on the leading edge of whatever is live.
   **The bars survive, inverted.** They were the only part of 242 that was never decorative — one per category actually found, width proportional to share — and on a dark ground a black bar is a hole rather than a mark, so the block becomes near-white and the ground shows through around it. Same meaning, drawn for the surface it now sits on. The mark was inverted, not abandoned.
   **White logo only.** The mark has a blue variant and it is not used: the reference allows one saturated element per view and that is the primary action. A coloured logo would be a second, competing with the thing the design wants looked at. It is inlined as SVG rather than loaded from `public/icons/`, because a popup is destroyed and rebuilt on every open, so a file fetch would happen every time and flash empty on first paint.

244. **A redesign that loses a feature is a regression wearing a new coat**
   — The first pass of the React popup shipped seven of the fifteen messages the old one sent. Manual marking, observe-only, clearing a scan, the scan record, the audit panel, the force-CPU toggle and the dev capture panel were all simply absent — not removed after a decision, just not carried across, and the build was green the whole time because nothing tests that a surface still offers what it offered yesterday.

Marking, observe-only, clearing and the scan record are restored. **What is still missing is named rather than quietly dropped:** the audit panel, the force-CPU toggle on the build line, and the `SHIELD_DEV` element-map export. The last matters most — it is the only way the benchmark corpus grows, and DECISIONS.md 183 is about that panel's gate failing in a way that read as working.

245. **The element-map export is restored behind a gate that is checked, not reasoned about**
   — 183 is the record of this panel's gate failing while reading as working: `panel.hidden = !__SHIELD_DEV__` hid markup that shipped anyway, with every listener attached, so anybody with devtools could unhide it and write a file of real field values. The imperative popup's answer was a top-level `if (__SHIELD_DEV__) wireCorpusCapture()`, which the define turns into `if (false)` and the bundler deletes along with everything it reaches.
   **The React rebuild moves that risk rather than removing it.** The gate is now a ternary around `<CorpusCapture />`, so what has to disappear is the *import* at the top of App.tsx — and whether it does is the bundler's judgement about whether that module is side-effect free, not anything a developer wrote. A refactor that gave the module a top-level side effect would defeat the gate while every test passed and the source still read correctly. That is the same failure shape as 183, one layer down.
   **So the bundle is grepped, in both directions.** `tools/check-dev-gate.mjs` runs after every build: the sentinel must be **absent** from a normal build and **present** under `SHIELD_DEV=1`. Failing the second direction matters as much as the first — a gate that silently removed the panel from dev builds would stop the benchmark corpus growing and nobody would notice until they tried to capture a page. Both failure modes were provoked deliberately and both exit non-zero; a check nobody has watched fail is not evidence.
   **The Firefox output is checked by name.** `dist-firefox` is a copy of `dist` taken after the Chrome check has already run, so it was covered only by the copy happening later and being faithful — two assumptions guarding the one capability in this codebase that writes real field values to disk. `build:firefox` now checks its own output.
   **What the panel looks like is part of the safety story.** A dashed amber edge, used by nothing else in the interface, so that a build which can write real field values to disk announces itself at a glance. Review before save is unchanged from the imperative version: nothing is written until the values have been listed and read, because "only capture when logged out" is unenforceable and being shown the contents is not.

246. **A test can outlive the thing it guards, and then it reports success about nothing**
   — `tests/dev-gate.test.ts` guarded `popup.ts`. 248. **The consent gate is wired, and the pause sits between the seal and the wire**
   — 240 settled what consent MEANS and built the pure half. This is the half that could not be pure: a promise the worker awaits, a broadcast to a popup that may not be open, and a timer.
   **The pause is placed after `buildSanitizedPayload` and before `send`**, because that is the only honest moment to ask. Earlier would describe a payload that does not exist yet; later would be asking about something already gone. Nothing about the pause makes the payload safe — it was sealed, order-checked and zero-leak swept before anyone was asked — and `awaiting-consent` is deliberately **not** in `STAGE_ORDER`, like `scanning` and for a related reason: adding it would let the order guard be satisfied by having asked, which would make consent part of what proves the payload safe. It is not.
   **One call site can approve, and it is behind an id check.** The id is the payload's own `request_id`, minted per step, so approval binds to a payload rather than to a run. Decline, timeout, stale id, a second ask starting underneath the first, a cancelled run and worker eviction mid-wait all end somewhere `mayTransmit` rejects. Pending state is held in memory and **not** persisted, on purpose: storage would create the single case this design otherwise does not have, an approval outliving the payload it was given for.
   **A rejected broadcast is not an error.** `chrome.runtime.sendMessage` rejects when no popup is listening, which is the ordinary case. Treating that as a failure would throw halfway through a run; it is caught and ignored, and the timeout is what that case resolves to.
   **The card does not steer.** Both choices are ordinary outlined buttons and neither is the gradient key control — a consent dialog whose approve button is the bright one is a dialog designed to be approved, and this feature exists for the person who wants to actually look. It shows counts, categories, frame size and destination, and links to the inspector for the bytes, because a second renderer of transmitted data is where the mistake would live.
   **The timeout is tested with fake timers rather than skipped.** A minute is too long to wait and "it probably times out" is the kind of assumption this project keeps finding to be wrong — and that path is the most likely way the feature is ever exercised: a popup opened, ignored, and closed.

   — Five fixtures test halves. Screens 1 and 2 have forms and no face; Screen 3 has a face and the reasoner is supposed to decline. 263. **The consent gate worked exactly once per popup session, and only a browser could have found it**
   — Found 2026-09-22 running the runbook's B2, which existed because 22 tests covered the gate and no browser had ever shown it. **The gate itself was never wrong. The bug was in who owns the status afterwards.**
   **What happens.** Starting a second run while the first is still waiting is legitimate — `askForConsent` opens with `resolve('stale')`, which abandons the first, and that is the design. The abandoned run then unwinds through the ordinary path and calls `setStatus('done')`. The popup clears the consent card on any status that is not `awaiting-consent`, which is correct on its own terms: a card left over from a finished run invites a click that authorises nothing. **But by then the card on screen belongs to the second run, which is still waiting.** It is wiped, nothing can answer it, and it can only time out.
   The console reads exactly as it should and still misleads, because the lines belong to a different run than the one the user is looking at:

   ```
   18:20:00.840  payload sealed - 14 elements, 3 manifest entries
   18:20:00.840  not transmitted - stale          <- run 1, abandoned by run 2
   18:20:00.842  finished without acting          <- run 1 setting the status
   ```

   **The reported symptom was "the second time I ran it, it did not ask".** That is precisely right, and the two-millisecond gap between those last lines is the whole defect.
   **Nothing leaked, and that is not luck.** Every abandoned run resolved to `stale`, `mayTransmit('stale')` is false, and no request was sent on any of the three runs. The gate failed closed exactly as 240 designed it to. What failed was usability: with "ask before sending" on, only the first run of a popup session could ever be answered.
   **The fix is that a superseded run writes nothing.** `StepOutcome` gains `superseded`, set only where `decision === 'stale'`, and the run loop returns on it before any branch that calls `setStatus`. The replacement owns the status; a run that has been replaced owns nothing. It logs nothing either — the user did not do anything, they started another run, and that run reports itself.
   **Why the fix could not go in the popup.** The popup receives `CONSENT_REQUESTED` for run 2 and then `STATE_CHANGED(done)` from run 1, in that order, with nothing in either message identifying which run it came from. **It genuinely cannot tell them apart.** Only the worker knows the first run was superseded, so only the worker can act on it.
   **Pinned by a test that was made to fail first.** Two tests cover the gate's side (a second ask abandons the first, the abandoned id cannot be approved afterwards). The fix itself is in the service worker, which cannot be imported under Node, so it is read as text — the same approach as 246's dev gate and for the same reason. The assertion is about ORDER: the superseded branch must precede every branch that sets a terminal status. Moving it below them was injected deliberately and the suite went to one failure, then passed again on restore. A first attempt at that test passed for the wrong reason, matching the word `setStatus` inside the branch's own explanatory comment; comments are now stripped before the check.
   **The general lesson, which is the same one as 246.** Both defects lived in code with tests around it, and both were invisible because the tests exercised the unit rather than the seam. 246's dev-gate tests guarded a file that had stopped being a build entry; these consent tests drove a gate in a world with no popup in it. **A component can be completely correct and still be wired to something that undoes it**, and only running it somewhere real shows that.
